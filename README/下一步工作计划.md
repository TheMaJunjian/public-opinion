## 1. 总判断

当前项目不应立刻进入真正的去中心化网络、上链、钱包登录或独立节点开发。

下一阶段的主线应是：

> 把当前中心化 Web 原型收束成一个可演示、可理解、可复算、可审计的协议原型。

换句话说，短期目标不是“去中心化”，而是让未来去中心化有可信地基：

- 用户能顺畅完成核心流程。
- 工程构建和测试能稳定通过。
- 状态变化能被导出、重放、校验。
- 贡献点、押注、结算和治理都能被解释为公开规则下的结果，而不是平台黑箱。

## 2. 取舍原则

### 2.1 文档不是命令，现实优先

现有文档包含不同阶段的想法，其中有些互相冲突，或超出当前工程和现实条件。之后执行时按以下顺序决策：

1. 真实代码状态。
2. 用户能否完成核心任务。
3. 数据是否可追溯、可复算。
4. 是否符合“消息与关系消息”为核心的长期结构。
5. 文档描述。

文档可以解释目标，但不能覆盖工程事实。

### 2.2 “一切皆消息”是方向，不是僵硬教条

消息化适合表达用户主动行为、治理提案、结算轮次、代码变更、运营公告。

但为性能、查询和一致性服务的派生表仍然允许存在，例如 Balance、BetPool、LedgerEntry、RevenuePool。关键要求不是“只存消息”，而是：派生状态必须能从公开事件或公开记录中解释和校验。

### 2.3 贡献点先作为测试经济，不作为金融承诺

当前贡献点应定位为产品内的测试账本和反滥用成本，不应对外表达为可投资资产、固定收益、替代货币或真实分红承诺。

在规则、复算、治理、收入来源都稳定前，贡献点只用于：

- 表达立场成本。
- 排序和过滤。
- 测试结算与推翻。
- 形成可审计的贡献记录。

### 2.4 操作体验优先于继续堆模型

公论的难点不是再增加几个模型，而是让普通用户理解并完成：

- 发消息。
- 选择消息或片段。
- 建立关系。
- 表态和押注。
- 发起结算。
- 看懂推翻和账本变化。
- 用清爽/聚焦视图降低信息噪音。

如果这些流程不顺，去中心化、治理和收入池都会变成用户无法使用的概念装饰。

## 3. 当前项目状态判断

### 3.1 已具备的基础

当前代码已经有较好的协议原型基础：

- 前后端分离：React/Vite + Express/TypeScript + Prisma/PostgreSQL。
- 统一 Message 模型已包含 TEXT、RELATION、ROUND、ROUND_RESULT、GOVERNANCE、CODE。
- 关系消息已经是一等实体，并支持递归指向关系消息。
- 已有贡献点、押注、BetPool、SettlementRound、LedgerEntry、Clawback、debtFrozen 等核心经济结构。
- 已有 AuditLog、RuleVersion、事件化写入路径。
- 前端已有 GraphView、SettlementPanel、RoundHistory、StanceHistoryPanel、AuditLogView、RevenuePanel、GovernancePanel、CleanFilterPanel 等组件雏形。
- 前端测试覆盖较多，图、布局、清爽视图、页面交互等都有测试。

这些说明项目不再是空想文档，已经进入“协议产品原型”阶段。

### 3.2 当前不稳定点

下一阶段必须先处理这些问题：

- 前端生产构建失败，当前 `tsc -b` 报 66 个 TypeScript 错误。问题不只是不补 `kind` 字段，还包括 mock API 缺少真实 API 方法、组件与 API 类型不同步、未使用变量、类型收窄错误、`content: undefined` 与 mock 类型冲突等。
- 后端测试不是全绿，当前 8 个测试套件中 2 个失败，合计 7 个失败用例。失败既包含旧测试预期与当前规则不一致，也包含 `events.ts` 中真实运行时错误。
- 前端测试能通过，但存在 React `act(...)` 警告，说明部分异步状态更新测试还不够稳。
- 前端 lint 目前失败，`npm run lint` 报 98 个 error、32 个 warning，其中大量来自 TopicDetailPage、GraphView 和既有 coverage 输出目录未排除。
- 治理和收入功能目前更接近界面/模型雏形，未形成完整闭环；相关 API 在真实 client 中存在，但 mock API 未同步，已经反向阻塞生产构建。
- 清爽/标签机制已有部分枚举、校验和展示痕迹，例如 SPAM、OFFTOPIC、LOWVALUE、IMPORTANT，但还没有形成完整的语义合同、最低成本规则、统计 API、默认折叠和 replay 可复算闭环。
- replay/verify 脚本缺失，无法证明数据库当前状态能由公开记录复算。
- `publicKey` 只是预留字段，尚未用于签名、事件认证或独立审计。
- TopicDetailPage 等前端核心页面承担过多职责，当前 TopicDetailPage 约 5127 行，长期维护风险已经升高。

### 3.3 关键结论

项目已经适合继续深挖，但不适合继续发散。

下一阶段要把“已有能力”变成“可靠闭环”，而不是继续新增大概念。

## 4. 下一阶段总目标

下一阶段命名为：

> 稳定演示版 + 公开复算前置版

目标是在一个可自托管实例中完成以下闭环：

1. 新用户注册登录。
2. 创建议题。
3. 发送消息并自动自押。
4. 对消息或片段建立关系。
5. 用 AGREE/DISAGREE 表达立场并形成经济权重。
6. 发起结算、投票、关闭结算。
7. 后续轮次可推翻前轮并触发 clawback。
8. 用户能看到账本、轮次历史、审计日志。
9. 用户能通过清爽/聚焦视图降低噪音。
10. 开发者能通过 replay/verify 工具复算关键状态。

达到以上目标后，再进入独立审计节点和更强去中心化设计。

### Phase B：核心演示流程与操作体验


目标：让一个新用户不看内部文档，也能完成公论的核心闭环。

优先级：高。

建议任务：

| 编号 | 任务 | 说明 | 验收 |
|---|---|---|---|
| B1 | 提前固定标签语义合同 | 并行定义 SPAM、OFFTOPIC、LOWVALUE、IMPORTANT 及其最低成本规则 | B 阶段 UI 不会因 C 阶段标签语义返工 |
| B2 | 定义标准演示剧本 | 固定一条最小流程：发消息、引用、反驳、赞同、结算、推翻、看账本 | 可在 10 分钟内演示完 |
| B3 | 梳理关系创建交互 | 明确 source、target、片段、关系消息目标的选择状态；减少隐藏规则 | 用户知道当前选了什么 |
| B4 | 优化发送与押注控件 | 发送即自押需要让用户看见成本、余额变化、失败原因 | 余额不足、冻结、自押金额都有清晰反馈 |
| B5 | 优化结算面板 | 让用户区分押注、投票、结算结果、推翻链、clawback | 用户能解释“为什么余额变了” |
| B6 | 改善审计入口 | AuditLog 不只是列表，应能按消息/用户/轮次跳转或过滤 | 演示时能追溯关键动作 |
| B6b | 优化拆分后的状态流 | 在 A6a 机械拆分基础上，整理 hook 接口、状态边界和错误反馈 | 页面逻辑更容易维护，行为更清晰 |

决策说明：

- 这里的重点不是“变漂亮”，而是“变可操作”。
- UI 应服务结构理解：让用户知道消息、关系、押注、结算之间发生了什么。
- 所有新增或修改的写操作，都必须保证 AuditLog payload 足以支持后续 replay/verify；如果暂时不能复算，必须在任务说明中记录缺口。
- 每个涉及写操作的任务完成时，都必须列出新增或修改的事件类型、AuditLog action、payload 字段，以及这些字段是否足以支持 replay；不能等到 Phase D 才集中补洞。
- B1 只固定标签语义和成本规则，不要求在 B 阶段完成标签统计、默认折叠和完整清爽视图。

### Phase C：清爽视图的公开化与持久化


目标：把当前本地清爽过滤器升级为可公开、可审计、可复算的反噪音机制。

优先级：高。

建议实现方向：

优先复用现有关系消息系统，不急着新增独立 TagAssignment 表。

也就是说，先把 SPAM、OFFTOPIC、LOWVALUE、IMPORTANT 表达为标准化 TAG 关系消息：

```text
用户 -> TAG 关系消息 -> 被标记的消息/关系/轮次
payload.label = SPAM | OFFTOPIC | LOWVALUE | IMPORTANT
stakeAmount = 标记成本
```

这样更符合当前“关系也是消息”的模型，也更容易被 replay 复算。

建议任务：

| 编号 | 任务 | 说明 | 验收 |
|---|---|---|---|
| C1 | 落地系统标签枚举 | 接收 B1 中已固定的 SPAM、OFFTOPIC、LOWVALUE、IMPORTANT，并接入前后端校验 | 前后端显示一致 |
| C2 | 落地标签成本 | 接收 B1 中已固定的最低成本规则，复用关系消息自押/锁定机制 | 滥用标签有成本 |
| C3 | 标签统计 API 或派生统计 | 可查询对象被哪些标签标记、数量、权重 | 清爽视图可稳定读取 |
| C4 | 默认折叠规则 | 达到阈值后默认折叠，但允许展开 | 不删除、不封禁，只改变视图 |
| C5 | 清爽视图与焦点模式兼容 | 过滤后关系显示仍保持可理解 | 图视图不出现断裂感 |

暂缓事项：

- 不先做复杂管理员治理。
- 不先做机器学习推荐。
- 不先做全局反作弊系统。

### Phase D：公开复算 replay/verify


目标：证明当前数据库状态不是黑箱，而是能从公开记录中重算。

优先级：高，是去中心化前置条件。

建议任务：

| 编号 | 任务 | 说明 | 验收 |
|---|---|---|---|
| D1 | 定义可复算范围 | 第一版只复算用户余额、PointAccount、Stake、BetPool、SettlementRound 结果、LedgerEntry 汇总 | 范围明确 |
| D2 | 编写 replay 脚本 | 从 AuditLog/LedgerEntry/PointTransaction 等公开记录构建派生状态 | 脚本能跑通 |
| D3 | 编写 verify 差异报告 | 对比 replay 结果与数据库当前状态 | 输出差异 JSON/文本报告 |
| D4 | 补审计字段缺口 | 如果 replay 发现 AuditLog payload 不足，补齐后续事件 payload | 新事件可复算 |
| D5 | 加入测试 | 构造小型场景验证 replay 与数据库一致 | 自动测试通过 |

决策说明：

- replay 不是附属工具，而是协议可信度的核心。
- 没有 replay，就不应进入独立审计节点。
- 如果某些历史事件信息不够，不强行修旧数据；先保证新事件完整。

---

### Phase E：治理闭环最小版本


目标：让规则修改不再只是“发一条治理消息”，而是进入可讨论、可表态、可结算、可应用的流程。

优先级：中。应在 Phase A-D 后进行。

建议任务：

| 编号 | 任务 | 说明 | 验收 |
|---|---|---|---|
| E1 | 治理提案结构化 | GOVERNANCE 消息包含提案类型、影响参数、预期 RuleVersion diff | 提案可被机器读取 |
| E2 | 治理投票复用 AGREE/DISAGREE | 不新增一套投票系统，继续复用关系消息和结算 | 投票路径一致 |
| E3 | 结算通过后进入待应用 | 通过不等于立即生效，先进入 PENDING_APPLY 并公开展示 | 避免误操作和暗箱执行 |
| E4 | 待应用公示期 | 在人工执行前保留公示窗口，允许用户继续反对、修正、发起新结算或撤回执行建议 | 人工执行前仍可被挑战 |
| E5 | 人工应用 + 审计记录 | 早期由运营者执行 RuleVersion 变更，但必须写 AuditLog，并关联治理消息、结算轮次和执行结果 | 现实可执行且可追责 |
| E6 | 延迟生效 | 新规则有明确生效时间，旧规则保留 | 规则切换可追溯 |

重要决策：

早期不做“代码自动部署”。

代码变更可以作为 CODE 消息被讨论和结算，但自动构建、自动部署风险过高，必须后置。当前阶段应采用“结算通过后人工执行，并公开记录执行结果”的半自动流程。

人工应用不是中心化后门，而是早期现实条件下的受审计执行器。提案从通过到应用之间必须有 PENDING_APPLY 状态和公示期，任何用户都应能在待应用期内继续表达反对、提交修正或发起新的结算。

---

### Phase F：收入池最小版本


目标：让 RevenuePool 从展示壳变成可记录、可审计的收入账本，但不承诺真实分红。

优先级：中低。治理闭环稳定后再做。

建议任务：

| 编号 | 任务 | 说明 | 验收 |
|---|---|---|---|
| F1 | 记录收入事件 | 支持运营者记录外部收入或测试收入 | 写入 AuditLog 和 RevenuePool |
| F2 | 记录分配规则 | 分配比例来自 RuleVersion 参数 | 分配有规则依据 |
| F3 | 测试分配 | 在测试贡献点体系内分配，不对外承诺收益 | LedgerEntry 可查 |
| F4 | RevenuePanel 展示来源 | 展示收入来源、分配对象、关联规则版本 | 用户能追溯来源 |

边界：

- 不接入真实支付。
- 不承诺投资收益。
- 不把贡献点宣传为现实金融资产。

---

### Phase G：渐进式去中心化入口


目标：在 replay 可靠后，开始让外部观察者独立验证系统。

优先级：后置。

进入条件：

- Phase A 全绿。
- Phase B 演示流程稳定。
- Phase C 清爽标签可审计。
- Phase D replay/verify 能稳定复算关键状态。

建议任务：

| 编号 | 任务 | 说明 | 验收 |
|---|---|---|---|
| G1 | 使用 publicKey | 用户可绑定公钥，新事件记录 actorPublicKey | 可从事件识别签名主体 |
| G2 | 事件签名 | 对关键写事件生成签名，服务端验证 | 伪造事件被拒绝 |
| G3 | 公开导出包 | 导出事件、派生状态摘要、verify 报告 | 外部可下载验证 |
| G4 | 只读审计节点 | 独立进程导入导出包并运行 verify | 审计节点能复算结果 |
| G5 | 状态哈希 | 为关键状态生成 Merkle root 或摘要哈希 | 后续可上链锚定 |

暂不做：

- P2P 网络。
- 链上执行。
- 钱包替代登录。
- 代币发行。

## 6. 冲突设计的当前裁决

### 6.1 管理员问题

早期文档中有“不设管理员”的表述，但现实中的自托管系统必须有运维者。

当前裁决：

- 协议层不设置“可任意改结果”的管理员。
- 实例层允许存在运营者和维护者。
- 运营者行为必须公开记录，并尽可能通过治理消息、AuditLog 和 RuleVersion 关联。

这比假装没有管理员更现实，也更可审计。

### 6.2 隐私公开与楚门主系统

楚门相关文档提出了更大的生活保障、隐私公开和成员等级体系。

当前裁决：

- 公论下一阶段不实现现实身份、生活账本、收入支出公开、成员等级和基础生活保障。
- 公论只先实现“公开讨论、公开规则、公开账本、公开复算”的软件地基。
- 楚门主系统可以未来建立在公论之上，但不应把所有社会制度一次性塞进当前产品。

### 6.3 贡献点与真实价值

贡献点的长期目标可以讨论，但当前不能当作真实货币或投资品实现。

当前裁决：

- 贡献点是测试经济和协议内成本。
- 收入池只做可审计记录，不做真实支付承诺。
- 分配规则先用于模拟和内部测试。

### 6.4 自动代码部署

CODE 消息和代码治理是有想象力的方向，但自动部署风险极高。

当前裁决：

- CODE 消息可以创建、讨论、押注、结算。
- 结算通过后只进入“建议执行”状态。
- 真实代码合并和部署仍由人工完成，并将执行结果写回系统。

### 6.5 ReadEvent 和阅读曝光

阅读记录有价值，但隐私和体量风险较高。

当前裁决：

- 暂缓 ReadEvent。
- 等核心讨论、结算、清爽视图、replay 稳定后再做。
- 做之前必须明确采集范围、开关、导出和删除策略。

## 7. 推荐执行顺序

### 第一优先级：必须立刻做

1. 修后端 `events.ts` 运行时 Bug，避免 settlement 路径继续 500。

5. 校准测试文档和启动文档，标明当前必须全绿的命令与已知门槛。
6. 对 TopicDetailPage 先做拆分盘点，再机械拆分，不改行为。
7. 明确前端 lint 是否纳入 A 阶段完成标准；若纳入，则先处理 coverage 排除和显著未使用变量。
8. 提前固定系统标签语义和最低成本规则。
9. 固定核心演示剧本。
10. 梳理关系创建和结算操作体验。

1. 治理闭环。
2. 收入池测试账本闭环。

1. 上链。

## 9. 一句话路线

先把公论做成一个可信的中心化协议原型，再让别人独立复算它，最后才谈真正去中心化。

当前最重要的工作不是“更宏大的机制”，而是：

> 构建全绿、流程顺畅、记录完整、状态可复算。
