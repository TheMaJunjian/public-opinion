# 服务器部署

运行时为 Node.js 24，消息、贡献点账本和结算记录保存在 PostgreSQL 16。API 同时提供前端静态文件，Caddy 提供同源 HTTPS。

服务器部署使用 GitHub Actions 构建的镜像。测试通过后，Actions 为 `main` 和 `codex/frontend-implementation-rewrite` 分支的每次提交构建 Linux amd64/arm64 镜像，发布到 `server-完整提交SHA` 的 GitHub prerelease，附带 SHA256SUMS。服务器只需 Git、Docker Compose、curl 和 sha256sum，不运行 npm、TypeScript 或镜像构建。镜像不含数据库、备份、迁移报告或本机配置。

已完成正式切换的服务器，日常更新只需运行一个命令：

```sh
bash /root/projects/public-opinion/deploy/update.sh
```

首次使用时，先在服务器仓库运行一次 `git pull --ff-only`，取得这个入口脚本。脚本自动定位仓库，显示当前分支、更新前的提交和镜像记录，执行 `git pull --ff-only` 后调用最新的 `deploy/deploy.sh --production`。它沿用当前分支及其上游，不切换分支；已跟踪文件有本地改动、没有上游分支或本地提交与上游不一致时会停止。忽略提交的 `.env.prod`、`.env.migration` 和 `.env.image` 不受干净工作区检查影响。

部署后自动显示新的 `.env.image` 和 Compose 服务列表，核对生产镜像与本次提交一致、PostgreSQL/API 健康、Caddy 运行，并在 API 容器中请求 `/api/health`，同时验证数据库连接。全部通过才输出成功；任一步失败都会以非零状态退出并显示失败阶段。这里检查容器和内部接口，公网域名、HTTPS 证书及外部访问仍需从浏览器验收。镜像尚未发布时，等 GitHub Actions 完成后重新运行同一命令即可。

当前已经迁移的数据先用只读演练启动。保留原 `deploy/.env.prod` 和根目录 `.env.migration`，停止此前手工运行、占用 33000 的 Node 服务，然后在同一个仓库目录运行：

```sh
git pull --ff-only
bash deploy/deploy.sh --rehearsal
```

脚本根据当前提交及服务器架构下载对应镜像，验证 SHA256 和镜像内的提交标记，再加载到 Docker。镜像尚未发布、下载失败或校验失败时停止，不替换现有 API。仓库公开，所以下载无需 GitHub 登录。`deploy.sh` 本身不拉取代码；日常生产更新由 `update.sh` 先完成拉取，再启动更新后的部署脚本。

演练读取 `.env.migration` 的 `MIGRATION_TARGET_DATABASE_URL` 和 `MIGRATION_TARGET_SCHEMA`，只将本机地址改成容器网络的 `postgres:5432`，保留目标库名、schema、账号和密码，不修改 `.env.prod` 的生产库名。启动前以只读事务检查目标的 settings、已有用户和 `read-only-rehearsal` 模式；空库、旧 Prisma 库、错误目标或其他模式都会拒绝启动，不初始化空站点。

API 在后台运行，绑定 `127.0.0.1:33000`，继续通过 SSH 隧道访问 http://localhost:33000。容器使用 `restart: unless-stopped`，SSH 断开后继续运行。脚本不创建或重启 PostgreSQL，只更新同一个 Compose 项目中的 API，不启动 Caddy。原数据库容器必须已运行；改目录或项目名导致找不到原容器时直接退出，避免误用新卷。

正式切换仍按 [PostgreSQL 服务器迁移](PostgreSQL服务器迁移.md) 完成最终备份和验收。在原 `deploy/.env.prod` 中明确设置已核验的最终数据库名，配置真实域名后运行：

```sh
bash deploy/deploy.sh --production
```

正式模式同样先校验已有库和用户，拒绝只读演练库，再更新 API 与 Caddy。服务更新使用 `--no-deps --no-build`，PostgreSQL 容器、原 Compose 项目及命名卷保持不变。脚本不会生成或改写数据库密码、覆盖配置、建库、恢复备份、重新迁移、执行 down、删除卷或清理旧镜像。

成功部署的镜像名记录在忽略提交的 `deploy/.env.image`。需要回到保留在本机的旧镜像时，可以显式指定 `bash deploy/deploy.sh --rehearsal --image gonglun:sha-旧完整提交SHA`。这仅回退应用镜像，不回退数据库；如果新版已产生业务写入，需先核验数据兼容性。

首次准备空服务器时根据 `deploy/.env.prod.example` 手动配置并按迁移说明先启动 PostgreSQL；本脚本用于已有站点和已迁移目标，不自动初始化新站点。`POSTGRES_PASSWORD` 可使用 `openssl rand -hex 32` 生成的十六进制字符串；已有数据库必须保留原密码。API 的 `DATABASE_URL` 由 Compose 使用同一密码构造。密码只在数据库卷首次初始化时设置，之后修改环境变量不会自动修改数据库内的密码。

第一位用户注册时需要输入 `.env.prod` 中的 `GONGLUN_FOUNDER_KEY`，以后正常注册无需此密钥。生产浏览器使用 HTTPS，以支持设备签名和安全会话。

```sh
cd deploy
docker compose -f docker-compose.prod.yml --env-file .env.prod ps
docker compose -f docker-compose.prod.yml --env-file .env.prod logs --tail=100 api postgres
```

PostgreSQL 使用 `postgres_data` 命名卷，挂载到 `/var/lib/postgresql/data`。更新镜像或重建容器会继续使用同一 Compose 项目下的原卷。生产 a5216ca 使用旧 Prisma 表结构，不能直接启动新版。换服务器时先按 [PostgreSQL 服务器迁移](PostgreSQL服务器迁移.md) 导出恢复旧库并验证旧版，再演练新版模型转换；新版会拒绝初始化旧 Prisma 库。

日常备份、恢复和清理旧镜像使用交互式维护脚本，在仓库根目录执行：

```sh
bash deploy/manage.sh
```

菜单提供备份、恢复到新数据库、删除指定旧应用镜像。运行时输入部署配置文件路径，默认使用原 `deploy/.env.prod`；沿用原部署目录及 Compose 项目名。如果原来设置了 `COMPOSE_PROJECT_NAME`，运行维护脚本时也须保留同一设置。每次操作前显示实际 API 容器使用的应用镜像、运行模式（正式或演练）、当前数据库名和 schema，不输出密码；数据库来自运行中 API 的实际配置。API 停止或不存在时明确显示当前库未能确认，不用默认库代替。备份显示本次选择的库，恢复同时显示当前库和新目标库；新库不会自动替换当前库。也可直接进入某个操作，其他参数仍按提示输入：

```sh
bash deploy/manage.sh backup
bash deploy/manage.sh restore
bash deploy/manage.sh images
```

备份会从运行中的 API 读取实际数据库名（含演练目标），由你确认后执行在线 `pg_dump -Fc`。API 不运行时必须手动输入核验过的库名，不默认备份 `gonglun`。备份保存到可指定的目录，默认在 `deploy/backups/库名-UTC时间戳.随机后缀/`，包含 `database.dump`、`metadata.txt` 和 `SHA256SUMS`。导出失败或归档目录无法读取时非零退出，文件夹保留 `.partial.` 标记，不报告成功。目录和文件默认仅当前用户可访问。请将整个成功目录复制到服务器之外，另行保管部署配置和密码；单库备份不包含 PostgreSQL 全局角色等对象。

恢复时输入服务器上的 `.dump` 文件路径和一个未使用的新库名。相对路径以执行命令时所在目录为准。脚本验证存在的校验文件，并检查归档目录；支持本脚本的 `SHA256SUMS` 以及此前单文件命令生成的 `.dump.sha256`（可迁移到其他路径）。没有校验文件的旧备份仍可恢复。只接受字母或下划线开头的小写字母、数字、下划线库名，最长 63 字符；不允许系统库。脚本从 `template0` 新建归 `gonglun` 所有的空库，用 `pg_restore --no-owner --no-acl --exit-on-error --single-transaction` 完整恢复。已有目标库直接拒绝；恢复失败保留新库供检查，不删除或覆盖原库，不停止应用，也不修改配置。

恢复成功只表示数据已导入新库，并显示库名与表数量，**网站尚未切换**。确认数据、schema 和应用版本兼容后再切换正式站点；旧 Prisma 备份须按迁移流程转换，不能直接启动新版。切换步骤：

1. 安排维护窗口，停止当前 API 的业务写入及其他写入进程。在 `deploy` 目录使用原配置执行 `docker compose -f docker-compose.prod.yml --env-file .env.prod stop api`，再用 `bash manage.sh backup` 手动输入原生产库名，保留最后一份备份。
2. 在原 `.env.prod` 中将 `GONGLUN_DATABASE_NAME` 改为恢复后的新库名，`DATABASE_SCHEMA` 使用备份所含的业务 schema。
3. 在仓库根目录执行 `bash deploy/deploy.sh --production`，它会先只读检查目标已有用户和数据库模式，再更新 API。使用自定义配置文件时，各命令都传入同一 `--env-file`。
4. 验证健康接口、登录、消息及余额。切换后业务数据回到备份时刻，备份之后的写入不会自动合并。原库继续保留；如果尚未在恢复库产生新写入，可改回原库名并重新部署以撤销切换。已产生新写入时先处理两库数据差异。

演练部署仍使用 `.env.migration` 的 `MIGRATION_TARGET_DATABASE_URL` 和 `MIGRATION_TARGET_SCHEMA`；恢复后如需切换演练目标，修改该配置并使用 `--rehearsal` 部署。

清理镜像时列出本机 `gonglun` 镜像，你输入并再次确认完整的 `gonglun:sha-40位提交SHA` 标签后才删除。部署记录中的镜像及仍关联任何容器（包括停止的容器）的镜像均拒绝删除。建议保留一个正常旧版本用于回退；脚本不使用全局 prune、强制删除、Compose down 或删除卷。旧迁移脚本 `export-production.sh` 保留原用途，仍固定导出旧版 `gonglun` 库，不用于新版日常备份。

若需手动备份，也可使用数据库自带工具，在 `deploy` 目录执行。下面以最终目标库 `gonglun_v2_final` 为例，必须替换成实际核验过的库名；只读演练通常为 `gonglun_v2_rehearsal`，不能继续备份默认的空 `gonglun` 库：

```sh
docker compose -f docker-compose.prod.yml --env-file .env.prod exec -T postgres pg_dump -U gonglun -d gonglun_v2_final -Fc -f /tmp/gonglun.dump
docker compose -f docker-compose.prod.yml --env-file .env.prod cp postgres:/tmp/gonglun.dump ./gonglun.dump
```

将生成的备份另存到服务器之外。`pg_dump` 可以在服务运行期间生成一致的数据库备份；不要把正在运行的数据库卷直接复制当作备份。恢复到已创建的空数据库时使用 `pg_restore`。参见 [PostgreSQL 备份说明](https://www.postgresql.org/docs/16/app-pgdump.html)。

应用健康检查为 `/api/health`。API 等待 PostgreSQL 健康后启动；外部只暴露 Caddy 的 80/443，API 3000 和 PostgreSQL 5432 均仅容器网络可访问。`TRUST_PROXY=1` 对应单层 Caddy 代理。

只有开发机或 CI 需要本地构建时，显式合并 `docker-compose.build.yml`，例如 `docker compose -f deploy/docker-compose.prod.yml -f deploy/docker-compose.build.yml --env-file deploy/.env.prod build api`。服务器正常部署不包含这个文件。
