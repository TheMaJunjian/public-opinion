# 公论（楚门计划）—— 价值证明共识系统设计文档

> 基于现有代码的演进路线：从结构化讨论平台 → 价值证明经济系统

---

## 一、核心概念

### 1.1 聊天游戏不是工作量证明，而是价值证明

| | 比特币（工作量证明） | 公论（价值证明） |
|------|---------------------|-------------------|
| 货币来源 | 挖矿凭空铸造 | 用户充值现实货币 1:1 锚定 |
| 价值锚定 | 算力成本（间接） | 系统总收入（直接） |
| 货币总量 | 算法固定 2100 万（通胀发行） | 充值多少发多少（永不虚增） |
| 收益模型 | 矿工获得新币奖励 | 持币者按比例获得收入分红 |
| 安全模型 | 用算力成本防作弊 | 用跨话题矛盾约束 + 质押博弈防作弊 |
| 共识对象 | 交易账本（谁给谁转了多少钱） | 观点真值（哪个命题是对的） |
| 裁判 | 不需要裁判，哈希说了算 | 不需要裁判，矛盾自指 + 经济博弈说了算 |
| 信任基础 | 密码学 + 物理能量 | 公开透明 + 博弈论 |

### 1.2 核心区分：数字货币 ≠ 加密货币

> "加密货币是用匿名性来保证安全的，公论的货币是数字货币，通过一切公开透明来保证安全。"

- **加密货币**（比特币）：无法确认"人"的身份 → 用"物"（电费/算力）的代价替代信任
- **数字货币**（公论）：公开透明规则 + 过程公开 + 经济制衡 → 用制度信任替代技术信任

## 二、经济模型

### 2.1 三层资金结构

```
┌──────────────────────────────────────────────┐
│              收入池（真钱）                     │
│  • 用户充值进入                               │
│  • 按贡献点持有比例定期分红                     │
│  • 永不增发，永不清算（除非提现）                │
└──────────────────┬───────────────────────────┘
                   │ 1:1 锚定
                   ▼
┌──────────────────────────────────────────────┐
│            贡献点（系统内积分）                   │
│  • 总贡献点 = 历史总充值额                      │
│  • 用于：发表内容、下注表态、质押挑战            │
│  • 在用户之间流转，总量不变                      │
└──────────────────────────────────────────────┘
```

### 2.2 资金流

```
用户充值真钱 → 获得等量贡献点
    │
    ├─→ 消耗贡献点发布内容（进入分红池）
    ├─→ 质押贡献点赞同/反对观点
    │       │
    │       └─→ 结算：胜方获得败方质押的贡献点
    │               │
    │               └─→ 提升下次分红的权重
    │
    └─→ 定期分红：收入池收益 × (你的贡献点 / 总贡献点)
```

### 2.3 下注即投票

- 用户用贡献点对观点表态（AGREE/DISAGREE）
- 下注总额多的一方获胜
- 胜方按比例瓜分败方质押的贡献点
- 没有中心裁判——纯代码自动执行

### 2.4 单注上限

可设单注金额上限（如每次最多 100 贡献点），防止大额玩家一次性碾压小额玩家。

## 三、共识机制：分层结算 + 矛盾约束

### 3.1 第一层：下注结算（快速共识）

```
AGREE 方总下注 500 点  vs  DISAGREE 方总下注 300 点
→ AGREE 方胜 → 胜方按比例瓜分 800 点奖池
```

### 3.2 第二层：矛盾证据挑战

```
败方不服 → 质押 N 点，提交 CORRECT 关系指向结算结果
主张："该结算应翻案，因为胜方中的某用户在话题B表达了相反立场"
    ↓
新一轮下注：
  「原结算正确」vs「原结算应翻案」
    ↓
挑战获胜 → 原结算翻案，挑战者获得原胜方的点
挑战失败 → 挑战者失去质押的 N 点
```

### 3.3 跨话题矛盾约束（核心创新）

**规则**：不需要软件自动检测矛盾——矛盾由**用户自己**发现和提交。

软件只需要提供两个能力：
1. **公开透明**：任何用户在任何话题中的 AGREE/DISAGREE 表态历史完全可查
2. **矛盾证据提交**：用户发现矛盾后，通过 CORRECT 关系 + 质押来发起挑战

```
矛盾证据提交流程：
  用户甲发现：用户乙在话题A AGREE「X为真」，在话题B AGREE「X为假」
    ↓
  用户甲提交 CORRECT 关系，目标指向话题A的结算结果
  附上证据："乙在话题B中表达了相反立场（链接）"
  质押 N 点
    ↓
  触发新一轮下注：
    「矛盾成立，应翻案」vs「矛盾不成立」
    ↓
  矛盾成立 → 原结算翻案，挑战者获利
  矛盾不成立 → 挑战者失去质押
```

**为什么不内建自动检测**：

- 矛盾检测是用户的经济行为——发现矛盾能赚钱，用户有动力自己去做
- 软件内建检测反而增加复杂度、消耗服务器资源，且无法覆盖所有矛盾类型
- 软件只做"公开透明"和"提交通道"就够了——这正是"制度信任"的体现

## 四、部署方案：Steam 免费游戏

### 4.1 Steam 兼容性分析

| Steam 政策 | 公论 | 合规 |
|-----------|------|------|
| 禁止加密货币/NFT | 贡献点是游戏内积分，不是加密货币 | ✅ |
| 允许内购（Steam 钱包） | 充值贡献点 = 标准内购 | ✅ |
| 禁止真实货币提现 | 贡献点不可提现，只可在游戏内使用 | ✅ |
| 反作弊要求 | 公开透明 + 矛盾博弈本身就是反作弊 | ✅ |
| 用户生成内容审核 | 讨论内容需有举报机制 | ⚠️ 需加举报功能 |

### 4.2 架构调整

```
Steam 客户端（Electron/CEF 封装前端）
    │
    │  HTTP/WebSocket
    ▼
┌─────────────────────────────────────┐
│         中心化游戏服务器               │
│                                     │
│  • 聊天消息存储与分发                  │
│  • 下注处理与结算（确定性算法）          │
│  • 贡献点账本（公开审计）               │
│  • Steam 内购验证                     │
│                                     │
│  公开透明机制：                        │
│  • 全部操作日志可通过只读 API 访问       │
│  • 任何人可独立验证结算结果              │
│  • 矛盾证据公开可见                     │
└─────────────────────────────────────┘
```

> Steam 要求游戏必须有服务器（单人游戏除外）。服务器负责运行游戏逻辑，但不等于"中心化裁判"——结算规则仍是确定性的，任何人都可以验证。

### 4.3 经济模型适配

| 原方案 | Steam 适配 |
|--------|-----------|
| 用户充值真钱 | Steam 内购（Steam 钱包支付） |
| 收入池分红 | ❌ Steam 不允许真钱分红 → 改为：贡献点本身即价值，可在游戏内消费 |
| 链上智能合约 | ❌ Steam 不允许 → 服务器端 PostgreSQL 公开账本 |

**调整后的价值闭环**：

```
用户 Steam 内购 → 获得贡献点
    │
    ├─→ 消耗贡献点发布内容
    ├─→ 质押下注 → 赢取更多贡献点
    │
    └─→ 贡献点多了 → 发言权重大 → 更有影响力
        （纯游戏内循环，不涉及真钱退出）
```

### 4.4 为什么中心化服务器 ≠ 中心化裁判

关键区分：

| | 中心化裁判 | 中心化服务器 |
|------|-----------|-------------|
| 谁决定对错 | 管理员主观判断 | 代码确定性执行 |
| 能否作弊 | 可以改结果 | 结算由公开算法执行，日志公开 |
| 信任来源 | 信这个人 | 信数学 + 信公开可审计 |

服务器只是"跑代码的机器"，不等于"有权力的人"。只要代码开源、日志公开，中心化服务器依然可以做到制度信任。

### 4.5 技术栈适配

| 层 | 当前 | Steam 调整 |
|------|------|-----------|
| 前端 | React + Vite | 封装为 Electron 或 Tauri 桌面应用 |
| 后端 | Express + Prisma | 不变 |
| 实时通信 | 待加 | WebSocket（聊天 + 下注广播） |
| 内购 | 待加 | Steamworks SDK 验证 |
| 部署 | Docker | VPS + PostgreSQL |

### 4.6 安全性

- Steam 账号绑定 → 天然 KYC，女巫攻击成本大增（注册 Steam 号有门槛）
- Steam 反作弊（VAC）→ 多一层防护
- 公开账本 + 矛盾博弈 → 原有安全机制不变

## 八、关键设计决策记录

1. **部署为 Steam 免费游戏** —— 中心化服务器 + 公开审计，Steam 内购替代真钱充值
2. **不凭空铸造货币** —— 贡献点 1:1 锚定充值，总量 = 历史充值总额
3. **不设中心裁判** —— 下注总量决定胜负，结算由确定性代码执行，日志公开可审计
4. **AGREE/DISAGREE 从纯表态升级为有经济权重的投票** —— 语义不变，加权重字段
5. **CORRECT 从纯语义标记升级为挑战上诉机制** —— 语义不变，加质押金额
6. **矛盾检测由用户完成，不由软件内建** —— 软件只提供公开透明 + 提交通道
