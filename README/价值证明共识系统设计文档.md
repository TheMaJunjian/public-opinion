# 公论（楚门计划）—— 去中心化价值证明共识与争议市场协议设计文档

> 长期目标：用可公开验证的价值创造、质押、举证、挑战和收益分配机制，建立一种可替代比特币 PoW 价值叙事的去中心化协议。

---

## 一、定位与边界

### 1.1 本系统是什么

公论的目标不是把聊天包装成普通平台积分，而是建立一种“价值证明”（Proof of Value）协议：让观点、证据、挑战、审计和共识修正成为可记录、可质押、可结算、可分配收益的公共工作。

- 用户围绕命题、观点和证据发表结构化内容。
- 用户用贡献点对观点表达 AGREE / DISAGREE 立场，并为立场承担成本。
- 系统按公开规则形成一个“当前共识状态”。
- 任何用户都可以基于公开历史提交证据、质押贡献点、发起挑战。
- 规则本身也可以成为公论中的讨论对象、质押对象、投票对象和迭代对象。
- 贡献点作为协议资产，用于质押、结算、治理和按规则分享协议收入。
- 共识结果不是绝对真理，而是可追责、可复查、可翻案、可审计的社会共识记录。

长期目标是：让贡献点像比特币一样不依赖中心化管理员、平台数据库或人工授权来决定发行和结算，但把价值来源从“消耗算力”迁移到“创造、验证和修正公共共识”。

一句话：

> 公论不替用户裁判真理，而是把观点、立场、证据、质押、收益和后续责任绑定到一条公开、可复算、可治理的价值记录上。

### 1.2 本系统不是什么

为了避免设计目标混乱，必须明确以下边界：

- 不是中心化平台积分，不由管理员任意增发、冻结、分配或终裁。
- 不是自动判断“谁说的是真理”的 AI 裁判。
- 不是承诺固定收益率、刚性兑付或由项目方担保的投资产品。
- 不是用“去中心化”掩盖黑箱规则；所有发行、结算、分配和治理规则必须公开可复算。
- 不是简单复制比特币 PoW，而是试图用价值证明取代纯算力消耗的价值证明逻辑。

### 1.3 与比特币 PoW 的关系

| 维度 | 比特币 PoW | 公论价值证明协议 |
|------|-------------|--------------|
| 核心目标 | 维护交易账本一致性 | 形成可挑战的公共共识和价值分配记录 |
| 工作对象 | 区块哈希计算 | 观点表态、下注、举证、挑战、审计和治理 |
| 验证方式 | 节点快速验证哈希难度 | 用户和审计节点复查公开规则、事件和资金流 |
| 安全来源 | 算力成本 + 密码学 | 质押成本 + 公开透明 + 可翻案机制 + 去中心化复算 |
| 资产形态 | BTC | 贡献点 |
| 价值来源 | 稀缺性 + 算力成本 + 网络共识 | 稀缺性 + 质押成本 + 有效贡献 + 协议收入分配 |
| 发行逻辑 | 区块奖励按规则释放 | 贡献点按公开规则铸造、解锁或分配 |
| 结果稳定性 | 链越长越难回滚 | 当前结果始终可用，后续仍可再次挑战 |
| 去中心化目标 | 矿工和节点共同维护账本 | 用户、审计节点和治理参与者共同维护规则与状态 |

公论要替代的不是比特币“公开账本、规则发行、无需中心化许可”的优点，而是比特币把价值证明绑定到哈希算力消耗上的路径。公论试图证明：公共讨论、事实纠错、证据审计和争议结算本身也可以成为可验证的价值工作。

## 二、核心概念

### 2.1 观点与关系

现有系统已经具备非线性讨论图的基础能力：Topic、Message、AGREE、DISAGREE、CORRECT 和 GraphView。新机制应尽量复用这些能力，而不是推翻重写。

| 概念 | 含义 | 工程映射 |
|------|------|----------|
| Topic | 一个讨论场域 | 现有 Topic 模型 |
| Claim | 可被支持、反对、修正的观点内容 | Message(TEXT) |
| Stance | 用户对观点的立场 | Message(RELATION) + AGREE / DISAGREE |
| Correction | 语义上的修正或反驳 | Message(RELATION) + CORRECT |
| Evidence | 支撑挑战的证据引用 | 新关系类型或 EvidenceRef 模型 |
| Wager | 用户为某个立场锁定的贡献点 | 新 Wager 模型 |
| Settlement | 某轮下注统计后的结算结果 | 新 Settlement 模型 |
| Challenge | 对结算结果发起的质押争议 | 新 Challenge 模型 |

### 2.2 关键拆分：CORRECT、EVIDENCE、CHALLENGE

原设计中 CORRECT 同时承担“纠错关系”和“经济挑战入口”，后续会导致状态机过重。新版设计将其拆分：

- CORRECT：语义关系，表示“我认为这条内容需要修正”。
- EVIDENCE：证据引用，指向内部消息、历史立场、结算记录或外部资料。
- CHALLENGE：经济动作，表示“我质押贡献点，请求系统重新进入争议流程”。

这样可以保留现有 CORRECT 的轻量表达能力，同时让真正涉及贡献点锁定、结算翻案的流程由 Challenge 模型管理。

### 2.3 共识状态不等于真理

系统中的结算结果只表示：

> 在指定规则、指定时间窗口、指定参与者和指定下注权重下，当前市场形成的暂定共识。

它不直接声明“该观点客观为真”。它的价值来自四点：

- 立场公开，谁支持过什么可以追溯。
- 成本公开，谁为观点承担了多少风险可以追溯。
- 证据公开，挑战依据可以被所有人复查。
- 历史公开，后续翻案会反向影响参与者信誉。

## 三、贡献点经济模型

### 3.1 贡献点是协议核心资产

贡献点不是普通平台积分，而是协议中的核心资产。它至少承担四个功能：

| 功能 | 含义 |
|------|------|
| 工作凭证 | 用户通过发言、举证、挑战、审计和治理贡献获得或解锁贡献点 |
| 质押资产 | 用户用贡献点为立场、挑战和规则修改承担成本 |
| 治理权重 | 用户可用贡献点参与规则讨论、提案、对决和版本迭代 |
| 收益分配凭证 | 协议收入可按公开规则分配给贡献点持有者、贡献者、审计者和公共池 |

早期实现可以使用测试网络贡献点验证规则，但文档目标不是停留在不可提现测试积分，而是逐步演进为无需中心化托管、可公开复算、可治理、可参与协议收入分配的贡献点系统。

### 3.2 账户与资产类型

| 类型 | 用途 | 是否协议核心 | 是否可分配收益 |
|------|------|--------------|----------------|
| 贡献点 | 发言、下注、挑战、治理、收益分配 | 是 | 是，按公开规则 |
| 协议收入池 | 汇集手续费、挑战罚没、服务收入或生态收入 | 是 | 用于分配、回购、销毁或公共建设 |
| 声誉值 | 衡量长期立场质量、有效挑战率和被翻案历史 | 可选 | 否，主要影响展示和治理参考 |
| 外部支付通道 | 充值、提现、法币或稳定币结算入口 | 非协议核心，可独立接入 | 否，只是出入金通道 |

贡献点是否可转让、是否总量固定、是否存在发行曲线，不应由本文档一次性拍板，而应由公论上的用户围绕规则提案公开讨论、质押、投票和迭代形成。为了接近比特币式可信货币属性，贡献点发行不应依赖管理员判断，而应依赖公开、可预测、可复算、可治理的规则演化过程。

### 3.3 规则自我迭代

公论不只记录外部世界的观点争议，也记录和处理自身规则的争议。贡献点发行、下注权重、挑战窗口、收益分配、治理门槛等具体参数，都应能作为规则提案进入公论本身的讨论图。

规则迭代的基本流程如下：

```text
用户提出规则修改提案
    ↓
围绕提案展开非线性讨论、举证和反驳
    ↓
提案者或支持者质押贡献点，表示愿意为规则承担成本
    ↓
用户对规则方案站队、下注或投票
    ↓
达到当前规则规定的通过条件
    ↓
生成新的 RuleVersion
    ↓
新规则延迟生效，旧规则和迁移记录永久可查
```

本文档只定义“规则如何被讨论和修改”的元规则；具体经济参数应尽量通过公论自身运行后的讨论和实践来获得。

### 3.4 贡献点状态

贡献点不应只有一个 points 数字，而应至少区分三种状态：

| 状态 | 含义 |
|------|------|
| available | 可用于发言、下注、挑战的余额 |
| locked | 已下注或已质押，等待结算或挑战期结束 |
| spent | 已作为手续费、惩罚或不可退成本消耗 |

建议用 PointTransaction 记录每一次变动，而不是只在 User 上维护一个 points 字段。

### 3.5 基础资金流

贡献点流转如下：

```text
系统按公开规则铸造 / 解锁 / 分配贡献点
    ↓
用户发言 / 表态 / 下注 / 举证 / 审计 / 治理
    ↓
下注或挑战贡献点进入 locked 状态
    ↓
结算后进入挑战期
    ↓
无挑战或挑战失败：贡献点按规则释放给胜方
有挑战且翻案：按翻案规则重新分配
    ↓
手续费、罚没、服务收入进入协议收入池
    ↓
按规则分配给贡献点持有者、有效贡献者、审计者和公共池
    ↓
记录完整 PointTransaction 和 AuditLog
```

### 3.6 协议收入与分红

分红是本协议的设计目标之一，但它不应由公司或管理员承诺固定收益，而应由协议收入和公开规则决定。换句话说：

> 有真实协议收入时，贡献点可以按规则参与分配；没有收入时，不存在项目方兜底收益。

可能的收入来源包括：

| 来源 | 说明 |
|------|------|
| 下注手续费 | 每次下注抽取极小比例进入协议收入池 |
| 挑战失败罚没 | 挑战失败者失去的质押按规则进入胜方、审计者或公共池 |
| 结算服务费 | 触发结算、导出审计、调用 API 等可收取协议费用 |
| 生态应用收入 | 基于公论协议构建的应用将部分收入回流协议池 |
| 链上托管收益 | 如果未来接入链上资产，托管或结算费用进入协议池 |

分配对象可以包括：

| 对象 | 分配依据 |
|------|----------|
| 贡献点持有者 | 按持有量、锁定量或长期参与权重分配 |
| 有效贡献者 | 按被支持、被引用、挑战成功或审计贡献分配 |
| 审计者 / 节点 | 按复算、验证、存储和可用性贡献分配 |
| 公共池 | 用于后续开发、激励、争议补贴和生态建设 |

具体分配比例不应写死在中心化后台，也不需要在本文档中提前确定。它应成为规则版本的一部分，由公论用户在公开讨论、质押、投票和复盘中持续调整。

## 四、下注与结算机制

### 4.1 下注即承担立场成本

用户对观点下注时，实际是在说：

> 我愿意为这个立场锁定一部分贡献点，并接受公开结算和后续挑战。

下注不是“买到真理”，而是让立场具备经济责任。

### 4.2 基础下注规则

| 规则 | 建议 |
|------|------|
| 下注对象 | 某条 Claim 或某个 Settlement |
| 下注方向 | AGREE / DISAGREE |
| 下注金额 | 大于最小值；早期版本可设置防误操作的单注保护上限 |
| 下注窗口 | Topic 或 Claim 创建后的一段时间 |
| 结算触发 | 到期自动结算，或任何用户手动触发到期结算 |
| 结算依据 | 有效下注权重，而不是简单人数 |
| 平局处理 | 退回本金，或延长下注期 |

### 4.3 权重与市场深度设计

争议市场不是一人一票系统。用户愿意承担更多质押风险，本来就应当在结算中获得更大权重。因此“有人押得多”本身不是错误，真正需要避免的是低成本操纵、误操作和规则不可解释。

建议采用更克制的设计：

| 策略 | 说明 | 建议 |
|------|------|------|
| 线性权重 | 有效权重等于下注金额 | 初始规则可默认使用，便于理解和复算 |
| 单注保护上限 | 防止用户误把全部贡献点压入一次下注 | 早期版本可选，作为 UX 保护而非长期反大户机制 |
| 平方根或分段权重 | 降低大额下注的边际权重 | 预留规则配置，是否启用由后续治理决定 |
| 单用户单市场硬上限 | 限制同一用户在同一市场累计下注 | 完整版不建议作为默认规则，容易削弱市场深度 |

早期版本可以先使用“线性金额 + 可选单注保护上限”，不急于实现复杂反大户机制。

### 4.4 结算示例

```text
观点：A 命题成立

AGREE 方有效下注：500
DISAGREE 方有效下注：300

结算结果：AGREE 暂定胜出
状态：SETTLED
下一步：进入 CHALLENGE_WINDOW
```

注意：此时只能说“AGREE 在本轮市场中胜出”，不能说“A 命题已经被系统证明为真”。

## 五、状态机与结果可用性

### 5.1 结算状态机

每个可下注对象都应有明确状态。系统允许无限翻案，但不能让结果长期不可用：任何时刻都应能查询到 `currentSettlement`，也就是最近一次有效结算形成的当前共识。

```text
OPEN
  ↓
VOTING
  ↓
SETTLED
  ↓
CHALLENGE_WINDOW
    ├─ 无有效挑战到期 → CURRENT
  └─ 有有效挑战 → CHALLENGED
                         ↓
                      REVOTING
                         ↓
                      RESETTLED
                         ↓
                  CHALLENGE_WINDOW

CURRENT
    └─ 后续有有效挑战 → CHALLENGED
```

### 5.2 状态说明

| 状态 | 含义 |
|------|------|
| OPEN | 观点可被讨论，市场尚未开始或刚创建 |
| VOTING | 用户可以下注表态 |
| SETTLED | 系统已按规则计算暂定结果 |
| CHALLENGE_WINDOW | 挑战期，胜方收益仍处于锁定或部分锁定 |
| CHALLENGED | 有人提交有效质押挑战 |
| REVOTING | 用户围绕挑战是否成立重新下注 |
| RESETTLED | 挑战轮已经重新结算 |
| CURRENT | 当前可用结算结果，奖励已按本轮规则释放，但后续仍可被新证据挑战 |

### 5.3 可用性与翻案规则

必须在产品规则中明确：

- 挑战期长度，例如 24 小时或 72 小时。
- 挑战冷却期，避免同一对象被连续刷挑战。
- 固定最低挑战质押，挑战失败即没收。
- 本轮结算奖励在挑战期内保持 locked。
- 挑战期结束后释放本轮奖励，结果进入 CURRENT。
- 后续翻案默认只改变当前共识和新一轮资金分配，不追回已经按当时规则释放的历史奖励。

建议早期实现采用更简单的规则：

- 结算结果一旦生成，立即成为 `currentSettlement`，供前端和 API 使用。
- 挑战期内，相关奖励暂不释放。
- 没有有效挑战时，挑战期结束后释放奖励，但不关闭未来挑战入口。
- 有有效挑战时，进入 REVOTING 并生成新的结算结果。

这样既避免“永远等待最终结果”，也避免为了无限翻案而引入复杂的历史追回和坏账机制。

## 六、矛盾证据与挑战机制

### 6.1 矛盾由用户发现，软件提供通道

系统不需要自动理解所有观点矛盾。它只需要提供三种能力：

- 所有用户的公开立场历史可查。
- 任何用户都可以引用历史消息和立场作为证据。
- 挑战者必须质押贡献点，避免低成本骚扰。

### 6.2 挑战流程

```text
用户发现可疑结算
    ↓
提交 Challenge
    ↓
锁定挑战质押
    ↓
附加 Evidence：历史立场、消息链接、结算记录、外部资料
    ↓
系统检查：目标是否处于可挑战状态、质押是否足够、证据是否格式完整
    ↓
进入 REVOTING
    ↓
市场围绕“挑战成立 / 挑战不成立”下注
    ↓
重新结算
```

### 6.3 跨话题矛盾示例

```text
用户甲发现：

用户乙在话题 A 中 AGREE “X 为真”
用户乙在话题 B 中 AGREE “X 为假”

用户甲提交：
- Challenge：请求挑战话题 A 的结算结果
- Evidence 1：用户乙在话题 A 的表态链接
- Evidence 2：用户乙在话题 B 的表态链接
- Bond：挑战质押 N 点

系统进入挑战轮：
- 选项一：矛盾成立，应翻案
- 选项二：矛盾不成立，维持原结算
```

### 6.4 挑战奖励与惩罚

| 结果 | 处理 |
|------|------|
| 挑战成立 | 挑战者取回质押，并获得挑战奖励或部分败方质押 |
| 挑战失败 | 挑战者失去质押，质押进入胜方或公共激励池 |
| 恶意重复挑战 | 固定最低质押 + 冷却期 + 失败没收；公开历史让重复失败者自行承担声誉成本 |
| 证据格式无效 | 不进入挑战轮，退回或部分扣除质押 |

早期实现可以先不做复杂主观裁判，只检查证据格式和状态合法性，让“挑战是否成立”本身进入下一轮市场表决。

## 七、公开性与反操纵边界

### 7.1 基本判断

本系统不优先依赖管理员封禁或人工裁决。多数异常行为在完全公开的账本中会自然暴露：谁下注、谁挑战、谁反复失败、谁与谁形成固定资金路径，都应当可以被任何用户查询和复算。

因此，反操纵的核心不是逐条预判所有恶意，而是确保三件事：

| 层面 | 设计要求 |
|------|----------|
| 规则确定 | 贡献点铸造、下注、结算、挑战、释放都按公开规则执行 |
| 成本真实 | 下注和挑战都需要锁定贡献点，挑战失败会损失质押 |
| 历史公开 | AuditLog、PointTransaction、立场历史和结算链全部可查 |

### 7.2 仍需内置的硬约束

| 问题 | 处理方式 |
|------|----------|
| 低成本刷挑战 | 固定最低挑战质押、失败没收、挑战冷却期 |
| 证据垃圾 | Evidence 必须引用已有消息、结算记录或 URL |
| 结算期间逃逸 | 挑战期内，本轮待释放奖励保持 locked |
| 女巫、合谋、自我交易 | 不优先强封，先通过公开账户、时间线和资金路径暴露 |

### 7.3 不设管理员角色

协议层不设置拥有特权裁决权的管理员。贡献点如何产生、参数如何调整、结算何时触发，都应由确定规则决定。后续如果需要修改规则，应通过公开治理或用户投票形成新的规则版本，而不是由管理员临时干预。

早期服务端实现即使仍由项目方部署，也不应在产品机制中引入“管理员发点”“管理员终裁”“管理员改结果”等特权动作。

## 八、审计日志与透明性

### 8.1 操作日志是系统安全的地基

“公开透明”不能只是一句原则，必须变成可查询、可导出、可复算的数据结构。

建议新增 AuditLog，记录所有会影响贡献点、立场、结算和挑战状态的事件。

### 8.2 事件类型

| 事件 | 含义 |
|------|------|
| USER_CREATED | 用户注册 |
| RULE_VERSION_CREATED | 初始规则或治理通过后的新规则版本 |
| POINT_MINTED | 系统按规则铸造或解锁贡献点 |
| MESSAGE_CREATED | 用户发布内容 |
| RELATION_CREATED | 用户创建关系，如 AGREE / DISAGREE / CORRECT |
| WAGER_PLACED | 用户下注，贡献点进入 locked |
| WAGER_CANCELLED | 允许取消时记录取消动作 |
| SETTLEMENT_CREATED | 系统生成结算结果 |
| CHALLENGE_CREATED | 用户发起挑战 |
| EVIDENCE_ATTACHED | 用户提交证据 |
| SETTLEMENT_RELEASED | 挑战期结束，本轮锁定奖励释放 |
| POINT_TRANSFERRED | 贡献点释放、奖励、惩罚或退回 |
| REVENUE_COLLECTED | 手续费、罚没或生态收入进入协议收入池 |
| REVENUE_DISTRIBUTED | 协议收入按规则分配给持有人、贡献者、审计者或公共池 |
| GOVERNANCE_PROPOSAL_CREATED | 用户发起规则修改提案 |
| GOVERNANCE_VOTE_CAST | 用户对规则修改提案投票 |

### 8.3 审计 API

建议后续提供：

- GET /api/audit-log：按时间查询全局事件。
- GET /api/topics/:id/audit-log：查询某个话题的事件。
- GET /api/users/:id/stances：查询用户公开立场历史。
- GET /api/settlements/:id/evidence：查询某个结算的证据链。

审计 API 是未来公开复算、用户治理、审计节点和链上托管的前置条件。

### Phase 7：渐进式去中心化（分四阶段演进）

去中心化不应一步到位，也不应推迟到最后才考虑。正确的路线是：先实现功能，但从一开始就按"未来可去中心化"的方式写代码；核心功能跑通后再逐步把关键状态迁移到可公开复算、独立审计、最终链上执行的架构。

```text
阶段一：事件化 Web 原型（与 Phase 1-6 并行）
    ↓
阶段二：公开复算
    ↓
阶段三：独立审计节点
    ↓
阶段四：关键状态上链
```

**阶段一：事件化 Web 原型**

继续使用当前的前后端 Web 架构（React + Express + PostgreSQL），但新增机制时遵守以下规则：

| 规则 | 说明 |
|------|------|
| 所有关键动作写 AuditLog | 不直接 update 最终状态而不留事件 |
| 贡献点变化写 PointTransaction | 余额、锁定、释放、罚没全部可追溯 |
| 状态可从事件重算 | 任何时刻的余额、结算结果、收入分配都能从事件日志重新计算 |
| 不允许直接改最终状态 | 结算、分配、释放都必须通过事件驱动 |
| 规则参数放入 RuleVersion | 不硬编码散落在业务逻辑里 |
| 结算函数尽量纯函数化 | 输入事件和规则版本，输出新状态 |

这一步仍然是中心化 Web 应用，但已经具备未来去中心化的数据基础。

**阶段二：公开复算**

下注、结算、挑战等核心机制跑通后：

| 任务 | 说明 |
|------|------|
| 导出事件日志 | 所有 AuditLog、PointTransaction、Settlement、Challenge、RuleVersion 可完整导出 |
| 导出规则版本 | 每个 RuleVersion 的参数和历史可查 |
| 编写 replay 脚本 | 从零消费事件日志，复算贡献点余额和结算结果 |
| 状态校验 | 对比数据库当前状态与 replay 结果，任何差异可被检测 |
| 快照 hash | 每个时间窗口生成状态快照 hash，供外部校验 |

这一步让系统从"只能信服务器"变成"可以验证服务器有没有作恶"。

**阶段三：独立审计节点**

| 任务 | 说明 |
|------|------|
| 独立节点程序 | 任何人可运行只读节点，拉取事件日志并复算状态 |
| 验证与告警 | 发现状态不一致时自动告警 |
| 公开状态 hash | 节点定期对外公布当前状态 hash |
| 多节点交叉校验 | 不同人运行的审计节点可互相校验 |

此时虽然资产和消息仍由主服务器托管，但已经不再是黑箱系统。

**阶段四：关键状态上链**

| 任务 | 说明 |
|------|------|
| RuleVersion hash 上链 | 规则版本 hash 写入链上，不可篡改 |
| Event batch hash 上链 | 定期将事件批次的 hash 锚定到链上 |
| 贡献点锁定/释放上链 | 贡献点的 locked/available 状态变更由智能合约执行 |
| 收益分配上链 | 协议收入池和分配结果由智能合约执行 |
| 重大治理结果上链 | 规则修改通过后，新 RuleVersion 生效由链上确认 |
| P2P 通信 | 消息和事件在多节点间同步，不依赖单一服务器 |
| 真实支付 / 稳定币入口 | 需要评估合规、风控、退款和资金托管，但不改变协议去中心化目标 |

不需要所有消息都上链（消息量大，先上 hash 更实际），但关键经济状态和规则变更应最终由链上合约执行。

### Phase 8：实现原则与架构约束

无论当前处于哪个阶段，以下原则应在开发早期就遵守：

| 原则 | 含义 |
|------|------|
| 事件优先 | 任何状态变更都通过事件表达，不直接修改最终状态 |
| 可重放 | 给定完整事件日志和规则版本，任何第三方都应能复算当前状态 |
| 无特权写入 | 代码层面不提供绕过事件日志直接改数据库的管理员接口 |
| 规则外置 | 经济参数、窗口长度、权重函数等不硬编码，而是从 RuleVersion 读取 |
| 可导出 | AuditLog、PointTransaction、RuleVersion 全部提供公开导出接口 |
| 先跑通再上链 | 核心经济机制在中心化环境下验证稳定后，再迁移到链上 |

## 十二、关键设计决策记录

1. 系统长期目标是以价值证明替代比特币 PoW 的算力价值证明路径。
2. 不宣称结算结果等于真理，只表示当前规则下的可挑战共识状态。
3. 贡献点是协议核心资产，可用于质押、治理和按规则参与协议收入分配。
4. CORRECT、EVIDENCE、CHALLENGE 分离，避免一个关系承担过多职责。
5. 所有下注奖励在挑战期内保持锁定，防止翻案坏账。
6. 不设置 FINAL 封口状态；系统允许无限翻案，但 `currentSettlement` 始终可用。
7. 公开透明必须落实为 AuditLog、PointTransaction 和可查询的立场历史。
8. GraphView 是核心解释界面，不只是可视化装饰。
9. 反操纵优先依赖公开账本、真实质押成本、失败没收和挑战冷却期。
10. 系统不设管理员角色，规则确定性执行，参数变更通过公论自身的讨论、质押、投票和审计形成新规则版本。
11. 本文档不替用户预先决定全部经济参数，只定义规则自我迭代所需的元机制。
12. 协议收入分配不由项目方承诺固定收益，而由真实收入和公开规则自动执行。
13. 去中心化采用渐进路线：先以事件化方式实现中心化原型，再逐步提供公开复算、独立审计节点，最后将关键状态迁移到链上执行。
14. 在任何阶段，所有状态变更都应通过事件表达且可从事件重放；不提供绕过事件日志直接修改最终状态的接口。

| 初始贡献点如何产生 | 按固定发行曲线、贡献行为或创世分配规则铸造 / 解锁 |
| 贡献点是否有总量上限 | 待定，可参考比特币固定上限或低通胀模型 |
| 协议收入如何分配 | 持有人、有效贡献者、审计者、公共池按规则分配 |
| 分红按持有量还是锁定量 | 推荐按长期锁定量或参与权重，避免短期套利 |
| 下注对象是 Claim 还是任意 Message | 先只允许 Claim / TEXT Message |
| 下注窗口多久 | 早期可设 24 小时或手动结算 |
| 挑战窗口多久 | 早期可设 24 小时 |
| 挑战冷却期多久 | 例如同一对象 1 小时内不能重复挑战 |
| 最低挑战质押 | 例如 10 点 |
| 平局如何处理 | 退回本金 |
| 挑战失败质押给谁 | 进入公共激励池或原胜方 |
| 是否允许撤下注 | 早期不允许，减少复杂度 |
| 是否启用平方根权重 | 先预留配置，默认线性，后续由治理决定 |
| 规则如何修改 | 后续通过用户投票生成新规则版本 |
| 何时链上执行 | 争议结算与收入分配规则稳定后启动 |

## 十四、结论

公论最有价值的方向，是把比特币“无需中心化许可、公开规则、可验证资产”的精神从哈希算力迁移到公共讨论和价值证明上：

> 观点不是免费漂浮的文字，而是带有历史、证据、成本和责任的公开承诺。

先把“元规则 + 规则迭代机制 + 贡献点 + 下注 + 结算 + 挑战 + 审计 + 收益分配”跑通，再逐步把关键状态迁移到链上或独立节点可复算的执行环境。这样路线更稳，也更能突出这个项目真正原创的地方：用图结构和质押机制，让公共讨论从情绪表达变成可追责、可分配、可自我迭代、可去中心化验证的价值证明市场。
