# 公论（楚门计划）—— 去中心化价值证明共识与争议市场协议设计文档

> 长期目标：用可公开验证的价值创造、质押、举证、挑战和收益分配机制，建立一种可替代比特币 PoW 价值叙事的去中心化协议。
>
> **结算模型：SRS 最终版** — 可重复结算 + 可回滚重分配 + 押注锁定 + 负债冻结。

---

## 一、定位与边界

### 1.1 本系统是什么

公论的目标是建立一种"价值证明"（Proof of Value）协议：让信息：内容、观点、证据、挑战、审计和共识修正，成为可记录、可质押、可结算、可分配收益的公共工作。

- 与会者围绕命题、观点和证据发表结构化内容。
- 与会者用贡献点对观点表达立场（PRO/CON），并为立场承担成本。
- 系统按公开规则形成"当前共识状态"。
- 任何与会者都可以发起新一轮结算来推翻旧共识。
- 规则本身也可以成为公论中的讨论对象、质押对象、投票对象和迭代对象。
- 贡献点作为协议资产，用于质押、结算、治理和按规则分享协议收入。
- 共识结果不是绝对真理，而是可追责、可复查、可翻案、可审计的社会共识记录。

一句话：

> 公论不替与会者裁判真理，而是把观点、立场、证据、质押、收益和后续责任绑定到一条公开、可复算、可治理的价值记录上。

### 1.2 本系统不是什么

- 不是中心化平台积分，不由管理员任意增发、冻结、分配或终裁。
- 不是自动判断"谁说的是真理"的 AI 裁判。
- 不是承诺固定收益率、刚性兑付或由项目方担保的投资产品。
- 不是用"去中心化"掩盖黑箱规则；所有发行、结算、分配和治理规则必须公开可复算。
- 不是简单复制比特币 PoW，而是试图用价值证明取代纯算力消耗的价值证明逻辑。

### 1.3 与比特币 PoW 的关系

| 维度 | 比特币 PoW | 公论价值证明协议 |
|------|-------------|--------------|
| 核心目标 | 维护交易账本一致性 | 形成可挑战的公共共识和价值分配记录 |
| 工作对象 | 区块哈希计算 | 观点表态、押注、举证、结算、推翻和治理 |
| 验证方式 | 节点快速验证哈希难度 | 与会者和审计节点复查公开规则、事件和资金流 |
| 安全来源 | 算力成本 + 密码学 | 质押成本 + 公开透明 + 可翻案机制 + 去中心化复算 |
| 资产形态 | BTC | 贡献点 |
| 价值来源 | 稀缺性 + 算力成本 + 网络共识 | 稀缺性 + 质押成本 + 有效贡献 + 协议收入分配 |
| 发行逻辑 | 区块奖励按规则释放 | 贡献点按公开规则铸造、解锁或分配 |
| 结果稳定性 | 链越长越难回滚 | 当前结果始终可用，后续仍可再次推翻 |
| 去中心化目标 | 矿工和节点共同维护账本 | 与会者、审计节点和治理参与者共同维护规则与状态 |

## 二、核心概念

### 2.1 观点与关系

| 概念 | 含义 | 工程映射 |
|------|------|----------|
| Topic | 一个讨论场域 | 现有 Topic 模型 |
| Claim | 可被支持、反对、修正的观点内容 | Message(TEXT) |
| Stance | 与会者对观点的立场 | Message(RELATION) + AGREE / DISAGREE |
| Correction | 语义上的修正或反驳 | Message(RELATION) + CORRECT |
| Evidence | 支撑挑战的证据引用 | EvidenceRef 模型 |
| Stake | 与会者对某条消息的押注（PRO/CON），锁定到 BetPool | 新 Stake 模型 |
| BetPool | 每条消息的资金锁定额（locked_pro / locked_con） | 新 BetPool 模型 |
| SettlementRound | 对某条消息的一轮结算（可重复、可推翻） | 新 SettlementRound 模型 |
| VoteStake | 结算投票押注（权重=金额，决定本轮 result） | 新 VoteStake 模型 |
| LedgerEntry | 账本分录（支持冲销与回滚重算） | 新 LedgerEntry 模型 |
| Balance | 与会者余额（可为负，debt_frozen 标志） | 新 Balance 模型 |

### 2.2 关键拆分：CORRECT、EVIDENCE 与多轮结算

- **CORRECT**：语义关系，表示"我认为这条内容需要修正"。保留现有轻量表达能力。
- **EVIDENCE**：证据引用，指向内部消息、历史立场、结算记录或外部资料。

而"推翻旧结算"不再需要独立的 Challenge 模型——在 SRS 模型中，**推翻就是发起新一轮 SettlementRound**。新轮次通过 `previous_round_id` 链式追溯，结算时执行 clawback 扣回上一轮分配并重新分配全部锁定资金。

### 2.3 共识状态不等于真理

系统中的结算结果只表示：

> 在指定规则、指定参与者和指定投票权重下，当前轮次形成的暂定共识。

它不直接声明"该观点客观为真"。它的价值来自：立场公开、成本公开、证据公开、历史公开。

## 三、贡献点经济模型

### 3.1 贡献点是协议核心资产

| 功能 | 含义 |
|------|------|
| 工作凭证 | 与会者通过发言、举证、审计和治理贡献获得或解锁贡献点 |
| 质押资产 | 与会者用贡献点为立场和规则修改承担成本 |
| 治理权重 | 与会者可用贡献点参与规则讨论、提案和版本迭代 |
| 收益分配凭证 | 协议收入可按公开规则分配给贡献点持有者、贡献者、审计者和公共池 |

### 3.2 账户与资产类型

| 类型 | 用途 | 是否协议核心 |
|------|------|--------------|
| 贡献点 | 发言、押注、投票、治理、收益分配 | 是 |
| 协议收入池 | 汇集手续费、罚没、服务收入 | 是 |
| 声誉值 | 衡量长期立场质量和被翻案历史 | 可选 |
| 外部支付通道 | 充值、提现、法币或稳定币结算 | 非协议核心 |

### 3.3 规则自我迭代

规则迭代的基本流程：

```text
与会者提出规则修改提案
    ↓
围绕提案展开非线性讨论、举证和反驳
    ↓
提案者或支持者质押贡献点
    ↓
与会者对规则方案站队、投票
    ↓
达到通过条件 → 生成新 RuleVersion
    ↓
新规则延迟生效，旧规则和迁移记录永久可查
```

### 3.4 贡献点状态

| 状态 | 含义 |
|------|------|
| available | 可用于发言、押注、投票的余额 |
| locked | 已押注或已投票，锁定在 BetPool 中 |
| spent | 已作为手续费、惩罚或不可退成本消耗 |

用 PointTransaction 记录每一次变动，而不是只在 User 上维护一个 points 字段。

### 3.5 基础资金流

```text
系统按公开规则铸造/解锁/分配贡献点
    ↓
与会者押注(PRO/CON) → 资金进入 BetPool locked 状态
    ↓
发起 SettlementRound → VOTING → 投票(VoteStake)
    ↓
结算 → 按 result 执行分账 → LedgerEntry: SETTLEMENT_PAYOUT
    ↓
后续可再发起新 Round 推翻 → LedgerEntry: SETTLEMENT_CLAWBACK
    ↓
手续费、罚没进入协议收入池 → 按规则分配
```

### 3.6 协议收入与分红

| 来源 | 说明 |
|------|------|
| 押注手续费 | 每次押注抽取极小比例 |
| 推翻失败罚没 | 恶意推翻者可能面临的成本 |
| 结算服务费 | 触发结算、导出审计等 |
| 生态应用收入 | 基于公论协议构建的应用回流 |

分配对象：贡献点持有者、有效贡献者、审计者/节点、公共池。具体比例由 RuleVersion 决定，通过公论自身的治理迭代。

## 四、押注与结算机制（SRS 模型）

> 本章采用 SRS 最终版模型。与早期"挑战窗口"模型的关键区别：结算不是终局，后续轮次可通过 clawback 推翻并重新分配全部锁定资金。

### 4.1 押注即承担立场成本

与会者对某条 Message 押注时，实际是在说：

> 我认为这条消息为 TRUE（PRO）或 FALSE（CON），我愿意锁定一部分贡献点，并接受公开结算和后续可能被推翻的风险。

### 4.2 基础押注规则

| 规则 | 说明 |
|------|------|
| 押注对象 | 任意 Message（TEXT 类型） |
| 押注方向 | PRO（认为消息为 TRUE）/ CON（认为消息为 FALSE） |
| 押注金额 | 大于最小值；从与会者 Balance 扣减并锁定到 BetPool |
| 锁定机制 | 下注时扣款，资金进入消息的 locked_pro 或 locked_con |
| 资金安全 | 押注资金不会消失——结算时按规则分配 |

### 4.3 数据模型

**Stake（押注记录）** — user_id, topic_id, message_id, side(PRO/CON), amount, round_id(nullable)

**BetPool（消息资金池）** — message_id(PK), locked_pro(int64), locked_con(int64)

**Balance（与会者余额）** — user_id(PK), balance(int64, 可为负), debt_frozen(bool)

> 冻结规则：balance < 0 → debt_frozen=true。冻结与会者禁止押注/投票/发起结算，允许阅读、发消息、建关系。

### 4.4 权重与结果判定

线性金额权重。对 SettlementRound 统计 VoteStake：

- weight_TRUE = sum(vote.amount where vote=TRUE)，FALSE/UNKNOWN 同理
- max 唯一 → result=该项；并列 → UNKNOWN

### 4.5 分账规则

| result | PRO 方 | CON 方 |
|--------|--------|--------|
| TRUE | 返本 + 按比例瓜分 CON | 损失本金 |
| FALSE | 损失本金 | 返本 + 按比例瓜分 PRO |
| UNKNOWN | 退回本金 | 退回本金 |

> 所有分配写入 LedgerEntry，后续轮次可通过 clawback 推翻。

### 4.6 结算示例

```text
Round 1: PRO=400, CON=200 → TRUE
  PRO 返本 400 + 瓜分 CON 200
  → LedgerEntry: SETTLEMENT_PAYOUT

Round 2: PRO=100, CON=350 → FALSE (推翻)
  先 clawback Round 1 → 若扣回不足 → balance<0 → debt_frozen
  再按 FALSE 执行新分账
```

## 五、轮次状态机与结算生命周期（SRS 模型）

> SRS 模型中，"推翻"不是通过独立的 Challenge 对象，而是发起新一轮 SettlementRound。

### 5.1 轮次生命周期

```text
OPEN  →  VOTING  →  SETTLED
  ↑                    ↓
  └── 之后可再创建新 Round（推翻旧结果）
```

| 状态 | 含义 |
|------|------|
| OPEN | 轮次已创建，尚未进入投票 |
| VOTING | 允许 VoteStake；也允许普通 Stake 追加（可归属 round_id） |
| SETTLED | 发起者关闭并结算，产生 result 并执行分账 |
| CANCELLED | 轮次被取消（可选） |

> 并发约束：同一 message_id 同时最多 1 个 status IN (OPEN, VOTING) 的 round。

### 5.2 数据模型

**SettlementRound**

| 字段 | 类型 | 说明 |
|------|------|------|
| round_id | PK | 轮次 ID |
| message_id | FK | 结算目标消息 |
| created_by_user_id | FK | 发起者 |
| status | OPEN/VOTING/SETTLED/CANCELLED | 当前状态 |
| result | TRUE/FALSE/UNKNOWN (nullable) | 结算结果 |
| previous_round_id | FK nullable | 链式追溯上一轮 |
| opened_at / closed_at | datetime | 时间窗口 |
| note | string optional | 备注 |

**VoteStake（投票押注）**

| 字段 | 类型 | 说明 |
|------|------|------|
| vote_id | PK | 投票 ID |
| round_id | FK | 所属轮次 |
| user_id | FK | 投票与会者 |
| vote | TRUE/FALSE/UNKNOWN | 投票方向 |
| amount | int64 > 0 | 投票金额（=权重） |
| created_at | datetime | 创建时间 |

> 与会者可多次投票，可改变投向（多条记录累计）。投票时从 Balance 扣款并锁定。

### 5.3 结算流程

```text
任何人 POST /api/messages/{id}/rounds → status=OPEN
    ↓
轮次进入 VOTING
    ↓
与会者 POST /api/rounds/{id}/votes（可多次）
    ↓
发起者 POST /api/rounds/{id}/close-and-settle
    ↓
系统计算 result → 执行分账 → status=SETTLED
    ↓
任何人可再创建新 Round（previous_round_id 链式追溯）
```

### 5.4 当前共识

任何时刻，对一条消息的有效共识 = 最近一次 status=SETTLED 的 round 的 result。

## 六、推翻与回滚机制（SRS 模型）

### 6.1 推翻即新轮次

不设独立的 Challenge 表。"推翻"就是创建新的 SettlementRound，其 `previous_round_id` 指向前一轮。新旧 result 不同时触发 clawback。

### 6.2 LedgerEntry（账本分录）

所有资金变动写入 LedgerEntry，支持冲销与回滚重算：

| entry_type | 含义 |
|------------|------|
| MINT_INITIAL / MINT_DAILY | 铸造/发放贡献点 |
| STAKE_LOCK / STAKE_UNLOCK | 押注锁定/解锁 |
| VOTE_LOCK / VOTE_UNLOCK | 投票锁定/解锁 |
| SETTLEMENT_PAYOUT | 结算分配 |
| SETTLEMENT_CLAWBACK | 推翻扣回 |

> balance = sum(LedgerEntry.amount)。推翻通过新增冲销分录实现，不做物理删除。

### 6.3 Clawback 流程

```text
Round N+1 结算前：
  1. 查 previous_round_id = Round N
  2. 若 Round N result ≠ Round N+1 result：
     a. 生成 SETTLEMENT_CLAWBACK 分录（从 Round N 赢家扣回）
     b. 若扣回导致某与会者 balance < 0 → debt_frozen=true
  3. 按 Round N+1 result 执行新分账
```

### 6.4 负债冻结

| 条件 | 效果 |
|------|------|
| balance < 0 | debt_frozen = true |
| debt_frozen = true | 禁止：押注、投票、发起结算 |
| debt_frozen = true | 允许：阅读、发消息、建关系、创建结论 |
| 还清负债 (balance >= 0) | debt_frozen 自动解除 |

### 6.5 反滥用

发送内容需锁定贡献点，被标注为无价值后扣除；标注同样需锁定贡献点。
表达立场消耗贡献点——押注失利者损失本金，负债者被冻结。

**经济成本即反滥用。** 每条操作都有代价，滥用的成本由滥用者自行承担。

## 七、公开性与反操纵边界

### 7.1 基本判断

反操纵的核心不是逐条预判所有恶意，而是确保三件事：

| 层面 | 设计要求 |
|------|----------|
| 规则确定 | 贡献点铸造、押注、结算、推翻都按公开规则执行 |
| 成本真实 | 押注和投票都需要锁定贡献点 |
| 历史公开 | AuditLog、PointTransaction、LedgerEntry、结算链全部可查 |

### 7.2 不设管理员角色

协议层不设置拥有特权裁决权的管理员。早期服务端即使由项目方部署，也不在机制中引入"管理员发点""管理员终裁""管理员改结果"等特权动作。

| VOTE_CAST | 与会者投票押注（TRUE/FALSE/UNKNOWN） |
| ROUND_SETTLED | 轮次结算，产生 result 并执行分账 |
| SETTLEMENT_CLAWBACK | 推翻扣回 |
| EVIDENCE_ATTACHED | 与会者提交证据 |
| POINT_TRANSFERRED | 贡献点释放、奖励、惩罚或退回 |

### 8.3 审计 API

- GET /api/audit-log：按时间查询全局事件

## 十、关键设计决策记录

1. 系统长期目标是以价值证明替代比特币 PoW 的算力价值证明路径。
2. 不宣称结算结果等于真理，只表示当前规则下的可挑战共识状态。
3. 贡献点是协议核心资产，可用于质押、治理和按规则参与协议收入分配。
4. CORRECT / EVIDENCE 分离，CORRECT 保留轻量语义关系。**推翻通过新 SettlementRound 实现，不设独立 Challenge 表。**
5. 押注方向为 PRO/CON，结算结果为 TRUE/FALSE/UNKNOWN 三方。
6. **结算可无限推翻**：后续轮次通过 clawback 扣回前轮分配并重新分账。
7. **负债冻结**：扣回不足时 balance 可为负，冻结与会者资金操作直到还清。
8. 公开透明必须落实为 AuditLog、LedgerEntry、PointTransaction 和可查询的立场历史。
9. 反滥用仅需依赖经济成本——每条操作都有代价，滥用者自行承担；公开账本确保可审计。
10. **发消息自动自押 PRO**：创建 TEXT/RELATION 消息时，自动按 selfStakeOnCreate 押注 PRO，统一押注管道（不再搞独立的"内容锁定"机制）。消息创建者的自押同时也意味着该消息的 BetPool 不为空，为后续结算提供基础。
11. **AGREE/DISAGREE 语义映射推迟**：赞同/反对目前走 RELATION 管道（押关系消息本身），其作为目标消息 PRO/CON 押注的语义映射推迟到 Phase 3 结算时统一处理。
12. 系统不设管理员角色，规则确定性执行，参数变更通过公论自身治理迭代。
13. 去中心化采用渐进路线：事件化原型 → 公开复算 → 独立审计节点 → 关键状态上链。
14. 在任何阶段，所有状态变更都应通过事件表达且可从事件重放。
