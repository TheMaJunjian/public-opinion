# 关系创建交互梳理

> 日期：2026-07-13
> 目的：梳理所有关系类型的创建路径，明确 source/target/文本三通道的交互逻辑，暴露隐藏规则，为后续 UI 优化提供依据。

## 1. 文档目的

本文档回答以下问题：

- 系统支持哪些关系类型？各自的语义是什么？
- 不同关系类型，用户在发送前，来源集合、目标集合、输入框文本三者如何组合决定最终行为？
- 哪些规则用户看不见但会影响结果？（隐藏规则）
- 当前交互有哪些痛点？改进方向是什么？

**读者**：前端开发、产品设计、交互优化相关成员。
**范围**：仅覆盖关系创建流程，不涉及视图渲染、布局算法、结算逻辑。

## 2. 关系类型总览

系统后端共注册 17 种关系类型。其中 `ALL_RELATION_TYPES` 列出 14 种（含 `tag` 作为标注入口），但标注的实际产品形态仅有 `recommend`（推荐标注）和 `archive`（冷藏标注）两种，`tag` 为 UI 选择器入口而非独立关系类型；`join` 随容器发送时创建。按语义分为 7 组：

> **关于「文本消息」与「关系消息」**：系统中消息分为两类 —— 用户输入的普通文本消息（`kind: "normal"`）和关系本身作为消息存在（`kind: "relation"`）。关系消息既可以被其他关系引用/标注，也可以进入结算流程。理解这一区分是理解 source/target 交互的基础。

### 2.1 边连接（引用与回复）

此类关系在 source（来源消息）和 target（目标消息）之间建立有向连线。

| 类型 | 中文 | 作用 | source 约束 | target 约束 | 附加关系 |
|------|------|------|-------------|-------------|----------|
| `annotation` | 注释 | 对目标消息附加一条注释说明（edge-label 展示），不影响目标内容本身 | 必须有（文本消息） | 文本消息或关系消息 | 无 |
| `reference` | 引用 | 将目标消息/片段作为论据或上下文引入当前消息，建立引用链 | 必须有（文本消息） | 文本消息或关系消息 | `evidence`（证据）/ `custom`（自定义标签） |
| `reply` | 回复 | 回复目标消息，形成对话树（`formsTrees: true`），是构建讨论结构的主要方式 | **可选**（有 source 时为附带文本的回复，无 source 时为纯立场回复关系消息） | 文本消息或关系消息 | `question`（疑问）/ `answer`（回答） |

- 附加关系在 UI 中通过"附加关系"下拉选择器呈现，选中后对应的边标签会替换默认类型名（如 `reply` → `疑问`）。
- `annotation` / `reference` 必须提供 source 文本消息（不在后端 `SOURCE_OPTIONAL` 集合中）。
- `reply` 在 `SOURCE_OPTIONAL` 集合中，可以无 source 直接回复关系消息。

### 2.2 立场表达

| 类型 | 中文 | 作用 | 附带文本时的转化 |
|------|------|------|------------------|
| `agree` | 赞同 | 对目标消息表达赞同立场，计入 stance 统计（`stanceEffect: support`） | 有文本 → 视为**支持**（SUPPORT 语义）；无文本 → 纯立场声明（decoration badge） |
| `disagree` | 反对 | 对目标消息表达反对立场，计入 stance 统计（`stanceEffect: oppose`） | 有文本 → 视为**反驳**（REBUT 语义）；无文本 → 纯立场声明（decoration badge） |

- 可纯立场（`sourceMessageId: null`，不附文本），也可附带文本消息。
- `agree`/`disagree` 每条边创建一个独立的关系记录。

#### 2.2.1 目标消息类型与转化

`agree`/`disagree` 的目标可以是任意类型的消息，但**具体行为因目标类型而异**：

| 目标类型 | 行为 |
|----------|------|
| 文本消息（`normal`） | 直接在目标卡片上展示立场徽章（赞同 / 反对），生成 stance 边 |
| 其他立场（`agree`/`disagree`） | 进入**立场链**（见 2.2.2），立场沿链传递到最终目标 |
| 标注消息（`recommend`/`archive`） | **后端转化**：不对标注本身表态，而是转为对标注所指向的文本目标创建同类型标注（如赞同推荐标注 → 创建推荐标注） |
| 容器（`classify`/`summary`/`merge`/`arrange`） | 作为对容器的投票，计入容器的 agree/disagree 计数，决定容器是否被**驳回**（见 2.2.3） |
| 其他关系消息（`reply`/`reference`/`annotation`/`correct`） | 直接对该关系消息表达立场，在关系消息卡片上展示徽章 |

#### 2.2.2 立场链（Stance Chain）

立场可以嵌套：对一条立场关系再表态，形成立场链。系统通过 `resolveUltimateStance` 将链传播到最终目标：

- **`agree` 不翻转**：赞同(赞同(X)) = 赞同(X)
- **`disagree` 翻转**：反对(赞同(X)) = 反对(X)；反对(反对(X)) = 赞同(X)

即每经过一层 `disagree`，有效立场翻转一次。链深度上限 20 层，检测环。

**示例**：
```
反对(rel-arr)                       → +1 反对 给 rel-arr
赞同(反对(rel-arr))                  → +1 反对 给 rel-arr（翻转一次）
反对(反对(rel-arr))                  → +1 赞同 给 rel-arr（翻转两次）
反对(赞同(rel-arr))                  → +1 反对 给 rel-arr（翻转一次）
```

立场链的传递结果通过 `computeTransitiveVoteStats` 汇总到最终目标，用于容器驳回判定和 stance 统计展示。

#### 2.2.3 容器投票与驳回

对容器关系（`classify`/`summary`/`merge`/`arrange`）的赞同/反对即为对该容器的投票：

- 当某容器的 `disagreeCount > agreeCount` 时，该容器被**驳回**（rejected）。
- 驳回的容器在视图中隐藏（不展示容器卡片），其内部消息回到父级画布。
- 用户仍可通过双击容器卡片进入**预览模式**（只读灰显）查看驳回的容器。
- 投票结果改变（赞同反超）后，容器恢复为活跃状态。

### 2.3 标注

标注类关系是 user→message 的关系（无 source 文本消息），在目标消息上展示 inline 徽章。系统共两种标注类型：

| 类型 | 中文 | 作用 | 标注理由 |
|------|------|------|----------|
| `recommend` | 推荐标注 | 对目标消息给出推荐评价，触发 **VALUE 结算**（自动押注），同用户对同一目标去重 | `payload.subType`：SPAM（垃圾）/ OFFTOPIC（跑题）/ LOWVALUE（低质）/ IMPORTANT（重要）/ CUSTOM（自定义） |
| `archive` | 冷藏标注 | 对目标消息给出冷藏评价，触发 **VALUE 结算**（自动押注），同用户对同一目标去重 | 同上 |

- 两种标注都触发 VALUE 结算，标注理由（`subType`）影响最低押注金额。
- UI 中通过选择 TAG 类型后从二级选择器指定推荐或冷藏来创建，不作为独立的关系类型按钮出现。
- `recommend`/`archive` 不在前端 `ALL_RELATION_TYPES` 中。

### 2.4 容器

容器类关系将多条消息组织为一个整体。容器内的消息通过 `JOIN` 关系（系统内部类型）记录成员资格。

| 类型 | 中文 | 作用 | 嵌套 |
|------|------|------|------|
| `classify` | 分类 | 将消息归入一个分类主题容器。被归入的消息在原画布中隐藏，显示在分类子画布中，双击分类卡片进入子画布查看 | ✅ target 可以是其他 CLASSIFY/MERGE/ARRANGE/SUMMARY 关系消息 |
| `summary` | 总结 | 对多条目标消息进行总结概括。source 消息在视图中**替换**目标消息展示（`replacesTarget: true`），原始目标变暗，双击可查看原文 | ✅ 同上 |
| `merge` | 归并 | 将多条消息归并入同一容器框架。**用途**：用户梳理固定的消息结构（如将分散的论点归并为一个论证组），归并后的消息仍在画布上可见，被一个 group 框架包裹 | ❌ |
| `arrange` | 排列 | 将消息按序排列入容器框架（支持纵向 `single-column` / 横向 `single-row`），通过 `secondaryRelationType` 选择排列方向 | ❌ |

- 容器都有 `isContainer: true`，在焦点模式中不作为距离跳点。
- `classify`/`summary` 目标可为空（创建空容器，后续追加）；`merge`/`arrange` 必须有目标。
- `classify`/`summary` 的 target 可以是其他容器关系消息，从而形成层级嵌套结构。
- 容器内的成员关系通过 `JOIN` 类型记录（`sourceMessageId` = 容器 ID, `targetRefs` = 成员消息）。
- 容器可被赞同/反对投票，触发驳回机制（见 2.2.3）。
- 容器嵌套：当容器 A 作为目标被另一个容器 B 引用时，A 通过 JOIN 关系整体加入 B。

### 2.5 更正

| 类型 | 中文 | 作用 | 附加关系 |
|------|------|------|----------|
| `correct` | 更正 | 用 source 文本替换目标消息中的内容（`replacesTarget: true`），形成更正链 | 当目标为关系消息时，可选择与被更正关系同 `PresentationKind` 的其他关系类型作为附加 |

- 更正目标为文本消息时：source 文本替换目标文本展示。
- 更正目标为关系消息时：可先创建一条新关系（由附加关系选择器指定类型），再用 CORRECT 指向旧关系，实现"更正关系的边"。
- `correct` 只能有一个目标。

### 2.6 治理

| 类型 | 中文 | 作用 |
|------|------|------|
| `proposal` | 提案 | 发起修改规则/制度的治理提案，可投票结算 |
| `code_change` | 代码变更 | 发起修改程序代码的提案，投票通过后自动部署 |
| `operations` | 运营公告 | 发布收入、统计等程序运营公告信息 |

- 治理类消息本身是独立消息（`kind` 为 `governance`/`code`/`operations`），**不允许有 source**（source 强制禁止）。
- 可以有 target（引用相关消息），但不强制。

### 2.7 加入

| 类型 | 中文 | 作用 |
|------|------|------|
| `join` | 加入 | 记录消息与容器之间的成员关系（`sourceMessageId`=容器ID → `targetRefs`=成员消息）。用户在发送容器关系（`classify`/`arrange`/`merge`/`summary`）时，为每个目标消息生成一条 JOIN 关系，作为「加入容器」消息卡片显示在视图中（`kind: "join"`） |

- `JOIN` 不在前端 `ALL_RELATION_TYPES` 中，不由用户从类型选择器中选择，而是由用户发送容器时触发创建。
- JOIN 消息在视图中以消息卡片形式呈现，但其边不在图中渲染（`modelBridge` 中跳过 JOIN 的 edge 创建）。
- 后端通过 JOIN 记录查询消息归属（如 `resolveMessageCanvas` 确定消息属于哪个容器）。

## 3. Draft → Source → Target 三通道状态机

用户选择消息和片段后，通过三个集合控制最终创建的关系形态。理解它们之间的流转是理解所有交互的基础。

### 3.1 三通道定义

```
点击/划选消息 → draftUnits（候选区）
       │
       ├─ commitDraftTo("source") → sourceUnits（来源集合）
       │
       └─ commitDraftTo("target") → targetUnits（目标集合）
```

| 通道 | 状态变量 | 填充方式 | 语义 |
|------|----------|----------|------|
| **Draft（候选区）** | `draftUnits` | 单击卡片（切换 whole）/ 划选文本（追加 fragment）/ 点击片段锚点 | 临时工作区，最终决定去向 |
| **Source（来源）** | `sourceUnits` | `commitDraftTo("source")` 从 Draft 移入 | 明确来源消息/片段 |
| **Target（目标）** | `targetUnits` | `commitDraftTo("target")` 从 Draft 移入 | 明确目标消息/片段 |

### 3.2 Draft 的快捷语义（当前实现 vs 设计意图）

**设计意图**：Draft 是万能暂存区，可提交到 Source 或 Target。发送时，Target 为空则 Draft 自动充当 Target（省去"加入目标集合"）；Target 非空则以 Target 为准。两者**同时非空**时应禁止发送——用户必须清空一边来消除歧义。

**当前代码实现**：Draft 无条件覆盖 Target，且两者同时非空时不拦截：

```typescript
// TopicDetailPage.tsx — handleQuickSendAndRelateFromDraftTargets
const effectiveTargets = draftUnits.length > 0 ? draftUnits : targetUnits;
```

**差距**：两者同时非空时应拒绝发送并提示"请清空候选区或目标集合"，而非静默选一边。这是 B3 痛点 **P1** 的根因。

### 3.3 三通道对最终行为的影响

根据关系类型和三通道状态，系统有 **6 种发送路径**：

| # | 条件 | 行为 | 适用类型 |
|---|------|------|----------|
| 1 | `relationType === null` | 只发文本消息，不创建关系 | 无关系类型 |
| 2 | `draftUnits.length === 0 && sourceUnits.length > 0 && targetUnits.length > 0` | 直接用来源集合→目标集合建立关系，**不创建新文本消息** | annotation, reference, reply, correct, agree, disagree |
| 3 | `draftUnits.length > 0`（有效目标非空） | 发送文本（如有）并建立关系，用 Draft 作目标 | 多数关系类型 |
| 4 | `draftUnits.length === 0 && targetUnits.length > 0` | 发送文本（如有）并建立关系，用 Target 作目标 | 多数关系类型 |
| 5 | `agree/disagree` 且无文本 | 纯立场声明，无 source 文本消息 | agree, disagree |
| 6 | TAG + recommend/archive | 无 source，直接创建标注关系 | tag → recommend/archive |

### 3.4 Draft 对发送按钮的约束

`singleButtonEnabled` 根据三通道状态和关系类型决定发送按钮是否可用。以下类型有**特殊约束**：

| 关系类型 | 特殊约束 |
|----------|----------|
| `classify` | 只需要文本非空（分类名称），不需要目标 |
| `summary` | 需要目标 + 文本非空（总结内容） |
| `merge` | 需要目标，**不需要**文本，且来源必须为空 |
| `arrange` | 需要目标，文本可选（有文本时文本消息也加入排列框架） |
| `governance/ops` | 来源必须为空，文本和目标至少一个非空 |
| `correct` + Draft 中有关系消息 | 文本必须为空，来源必须为空（通过附加关系选择器选新边类型） |

### 3.5 界面示意

```
┌─ Draft（候选区）─────────────────────┐
│  msg-001 [whole]  msg-002 [frag:0-5] │
│  [清空]  [加入来源集合] [加入目标集合]   │
└──────────────────────────────────────┘
┌─ Sources ──────┐  ┌─ Targets ──────┐
│  msg-003 [whole]│  │  msg-004 [whole]│
└────────────────┘  └────────────────┘
```

## 4. 隐藏规则

以下规则影响实际行为但用户在 UI 中不易直接察觉。

### 4.1 立场表态的目标自动转化

对标注消息（`recommend`/`archive`）表态时，后端**自动转化**目标：

| 操作 | 后端实际行为 |
|------|-------------|
| 赞同(推荐标注) | → 自动对推荐标注指向的原始文本创建推荐标注 |
| 反对(推荐标注) | → 自动对原始文本创建冷藏标注 |
| 赞同(冷藏标注) | → 自动对原始文本创建冷藏标注 |
| 反对(冷藏标注) | → 自动对原始文本创建推荐标注 |

用户以为自己在"赞同一条推荐"，实际上系统把它变成了"对原文也推荐一次"。这个转化在 `backend/src/lib/events.ts` 的 `resolveAnnotationTarget` 中实现。

### 4.2 立场链的翻转语义

对立场表态再表态时，`disagree` 会翻转有效立场：

```
反对(赞同(X)) = 反对(X)    ← 翻转
反对(反对(X)) = 赞同(X)    ← 翻转
赞同(赞同(X)) = 赞同(X)    ← 不翻转
赞同(反对(X)) = 反对(X)    ← 不翻转
```

链深度上限 20 层，检测环。用户看不到中间立场链的传递过程，只看最终汇总。

### 4.3 文本输入的双重身份

某些关系类型的文本输入**不是**独立文本消息，而是关系 payload 的一部分：

| 关系类型 | 文本去向 |
|----------|----------|
| `classify` | `payload.title`（分类名称） |
| `summary` | `payload.title`（总结标题） |
| `merge` | 不允许有文本 |
| `arrange` | 有文本时创建独立文本消息 + JOIN（文本消息也加入框架） |
| `tag` | `payload.label`（标注文本） |
| `proposal/code_change/operations` | `payload.content`（提案正文） |
| 其他类型 | 独立文本消息（`kind: "normal"`），作为 source |

这对押注计算有影响：当文本进入 payload 时，不收取"文本消息押注"，只收取"关系押注"。

### 4.4 SOURCE_FORBIDDEN 类型

以下类型**禁止**带 `sourceMessageId`（后端强制校验）：

| 类型 | 原因 |
|------|------|
| `recommend` / `archive` | 标注是用户→消息的关系，无来源文本 |
| `proposal` / `code_change` / `operations` | 治理消息本身独立存在 |

前端 `singleButtonEnabled` 中通过 `isGovernanceOrOpsType && sourceUnits.length > 0 → false` 做了软拦截，但后端还会做最终硬校验。

### 4.5 CORRECT 的两种模式

`correct` 的行为因 Draft 中是否包含关系消息而完全不同：

| Draft 状态 | 行为 |
|------------|------|
| 全是文本消息 | 用 source 文本替换目标文本内容，在目标卡片上显示更正标记 |
| 包含关系消息 | **不创建 source 文本**，通过附加关系选择器选新边类型，创建新关系 + CORRECT 指向旧关系 |

后者在界面上的提示是"更正关系目标为关系消息时不应有文本"——前端强制清空文本输入框。

### 4.6 ARRANGE 布局锁定

当 Draft/Source 中包含已存在的 ARRANGE 关系消息时，`secondaryRelationType` 被锁定为该 ARRANGE 的当前布局方向（`vertical`/`horizontal`），用户无法切换。这防止了追加到已有排列框架时布局不一致。

### 4.7 容器驳回的隐藏规则

- 驳回条件：`disagreeCount > agreeCount`
- 被驳回的容器在视图中隐藏，但**仍可通过双击进入预览模式**（只读灰显）
- 投票变化后容器**自动恢复**，无需手动操作
- 驳回仅影响视图渲染，不删除数据

### 4.8 JOIN 关系的创建

用户发送容器关系时，每个目标消息创建一条 JOIN 关系（`stakeAmount=1 + burn`），用户看不到这个过程但会被扣点。`totalConsumption` 计算中列出了 `joinCount` 和 `joinStakeTotal`，但仅在字符串"总计 X 点"中显示，容易忽略。

## 5. UI 痛点与改进建议

### 5.1 痛点

#### P1: Draft 和 Target 同时非空时不拦截

`effectiveTargets = draftUnits.length > 0 ? draftUnits : targetUnits` 在两者同时非空时静默选 Draft。用户先提交消息到 Target，再点击新消息（进入 Draft），发送时 Target 被忽略且无任何提示。

**根因**：两者同时非空是歧义状态，应拒绝发送并提示"请清空候选区或目标集合"。

#### P2: 关系类型按钮过多（14 个平铺）

14 个按钮一字排开，无分组、无优先级、无视觉层级。新用户面对一整排按钮不知所措。

**现状**：`ALL_RELATION_TYPES` 14 个按钮全部渲染，TAG 和其他按钮混在一起。

#### P3: 发送按钮状态分散在多个条件中

`singleButtonEnabled` 和 `singleButtonLabel` 合计约 160 行条件逻辑，混合了 14 种关系类型的特殊规则、Draft/Source/Target 状态、押注校验、余额校验。

**现状**：新增或修改关系类型时，需要同时修改 `singleButtonEnabled`、`singleButtonLabel`、`handleQuickSendAndRelateFromDraftTargets` 三处逻辑，容易遗漏。

#### P4: 文本身份不透明

用户输入文本后，切换关系类型时文本可能从"独立消息"变成"payload 内容"，反之亦然。但用户看不到这个转化——只有通过"总计 X 点"中间的文本押注是否消失来推断。

**现状**：`isTextInPayload` 列表硬编码在 `totalConsumption` 计算中。

#### P5: 押注预览缺少"操作后余额"

当前显示"总计 25 点 / 可用 100"，但没有显示"操作后剩余 75 点"。用户需自己心算，在涉及冻结金额时尤其困难。

**现状**：`totalConsumption` 计算了总消耗，但只显示消耗侧，不显示余额变化。

| S2 | 将关系类型按钮按语义分组（边连接 / 立场 / 容器 / 标注 / 治理），使用折叠面板或标签页 | P2 | 中 |
