# 历史价值投票消息恢复

数据库版本 9：`correct-historical-value-vote-messages`，由独立的 `apps/migrate` 程序执行。版本 8 修复的是旧结算消息目标；版本 9 修复此前价值仲裁投票被保存为赞同／反对的问题。

根据消息保存的轮次、执行地址和方向，将价值投票原消息转换为推荐／冷藏，并恢复对原评价对象的准确引用。普通真假投票、正文讨论，以及仅与旧价值轮次共用消息地址的赞同／反对保持原样。

迁移同时更新当前消息、修订历史、变更记录、请求结果缓存、引用索引和个人标记，并发布同步变更。消息 ID、作者、原时间、修订号和投入金额保持不变；原记录保存在私有的 `value_vote_message_backups` 中。请求输入和签名原文不修改。余额、账本、轮次、押注、执行记录和签名前后校验一致，不重新执行投票或结算。目标无法确认时整体回滚，版本 9 不登记；重复运行不重复修复或追加同步事件。

## 生产执行

发布包含版本 9 的镜像。沿用[旧结算引用恢复的备份、维护窗口和迁移步骤](旧结算目标引用恢复.md)，不需要为这项修复另找旧服务器备份：价值投票的轮次和执行依据已经存放在当前数据库中。

在部署仓库根目录执行：

```bash
bash deploy/manage.sh backup
compose=(docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env.prod)
"${compose[@]}" stop api
"${compose[@]}" run --rm --no-deps -T api node apps/migrate/dist/migrate-cli.js --plan
"${compose[@]}" run --rm --no-deps -T api node apps/migrate/dist/migrate-cli.js
"${compose[@]}" run --rm --no-deps -T api node apps/migrate/dist/verify-current-cli.js
"${compose[@]}" up -d api
```

`DATABASE_URL`、业务 schema 和候选镜像须沿用当前部署配置。预检的 `valueVoteMessages.pending` 是待转换消息数，`unresolved` 应为 0；验证应返回 `verified: true`，两项均为 0。新版 API 启动发现旧版本时，也会调用同一独立迁移程序完成版本 9；仍需在发布前备份并完成验证。

如需回退，使用升级前备份恢复到独立数据库并按现有部署流程切换；旧镜像不支持直接访问已经登记版本 9 的数据库。
