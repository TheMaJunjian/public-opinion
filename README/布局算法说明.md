# 非线性结构视图布局算法说明

> 本文档梳理 `GraphView.tsx` 中非线性结构视图的布局算法，按关系类型分组说明每种关系消息对其来源消息和目标消息的布局影响。

---

## 一、布局流程总览

> **基础排序**：所有消息（文本消息与关系消息）在进入布局管线之前，已按创建时间升序排列。这意味着同列内消息从上到下遵循发言先后顺序，框架型内部子消息也按时间排布。这一排序是"会议发言顺序"的根基——谁先发言，谁就在上方；谁后回应，谁就在下方。

```
原始消息 + 关系
      │
      ▼
┌─────────────────────────────────────────────────────┐
│  Stage 1: 列分配（Column Assignment Pipeline）        │
│                                                       │
│  ① computeMinColumnsForAnnoRefRule1  ← 注释/引用约束   │
│  ② applyReplyLayoutAdjustments       ← 回复列偏好      │
│  ③ applyAgreeDisagreeColumnOverride   ← 赞同/反对列约束 │
│  ④ applyGroupingColumnOverride        ← 排列/更正（归并跳过此步）│
│                                                       │
│  输出: colOf[消息ID] → 列号                            │
└──────────────────────┬────────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────┐
│  Stage 2: 二维排布（No-Overlap Layout）                │
│                                                       │
│  ⑤ buildFrameBlocks                  ← 识别所有边框组  │
│  ⑥ computeNoOverlapLayout            ← 递归排布+无重叠 │
│  ⑦ computeFrameAwareColumnCorrection ← 帧感知列修正    │
│     （帧间水平重叠时微调相关消息列号）                  │
│  ⑧ compactAnnoRefClusters            ← 注释/引用聚类压缩│
│     （将 anno/ref 链上的消息向左收紧，消除多余列间距）   │
│  ⑨ buildFrameAvoidanceReservations   ← 边框避让        │
│  ⑩ applyFrameAvoidanceReservations   ← 应用避让        │
│  ⑪ applyMergeCanvasReservations      ← 归并画布调整    │
│                                                       │
│  输出: layout[消息ID] → {x, y, width, height}          │
└──────────────────────┬────────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────┐
│  Stage 3: 边与装饰渲染（Edge Routing & Decorations）    │
│                                                       │
│  ⑫ 计算连线箭头 (quadratic Bézier curves)              │
│  ⑬ 计算赞同/反对徽章位置                               │
│  ⑭ 计算TAG标签徽章位置                                 │
│  ⑮ 计算排列边框 / 归并边框 / 总结覆盖层                 │
│  ⑯ 计算行内徽章 (RECOMMEND / ARCHIVE)                  │
└─────────────────────────────────────────────────────┘
```

### 布局常量

| 常量 | 值 | 说明 |
|------|-----|------|
| `CARD_W` | 320px | 卡片最小宽度 |
| `MIN_CARD_H` | 86px | 卡片最小高度 |
| `GRID_LEFT` | 18px | 网格左边界 |
| `GRID_TOP` | 48px | 网格上边界 |
| `COL_GAP` | 80px | 列间距 |
| `ROW_GAP` | 32px | 行间距 |
| `FRAME_PAD` | 16px | 边框包围盒外边距（用于计算边框矩形） |
| `FRAME_PAD_X` | 18px（= GRID_LEFT） | 边框内部水平内边距（内容区 X 偏移） |
| `FRAME_PAD_Y` | 48px（= GRID_TOP） | 边框内部垂直内边距（内容区 Y 偏移） |

> **起始位置不变性**：画布上的视觉单元分为两类——**消息卡型**（文本消息、分类/总结主题卡）和**框架型**（排列、归并）。两者共用同一套外层布局逻辑：作为整体，它们在画布上的排布规则完全一致。空白画布时，两者的左上角均位于 `(GRID_LEFT, GRID_TOP) = (18, 48)`；画布已有内容时，新增的消息卡型与框架型同样通过 `findY2` 找到相同的避让起始位置，框架边框由此向外扩展 `FRAME_PAD`。区别在于框架型需要额外处理内部子消息的排布，但这不影响其作为一个整体参与外层布局的方式。
>
> 其余关系类型（赞同/反对装饰、TAG 标签、更正徽章、行内徽章）依附于上述两种视觉单元渲染，不参与独立的二维排布。
>
> 这一不变性是"**关系消息也是消息**"这一核心设计原则在布局层面的体现：无论消息的 `kind` 是 `normal`（文本消息）还是 `relation`（关系消息），在画布上的外层排布逻辑保持一致。关系消息只是带有附加语义（连线、边框、徽章等）的普通消息。

## 二、关系类型的布局影响（按类别分组）

### 第一类：连线标注（ANNOTATION / REFERENCE / REPLY）

> **PresentationKind**: `edge-label` — 渲染为带可点击标签的有向曲线。

这三种关系类型共享相同的渲染方式（SVG 二次贝塞尔曲线 + 文字标签），但在列约束和树结构上有区别。

#### ANNOTATION（注释）

| 属性 | 值 |
|------|-----|
| PresentationKind | `edge-label` |
| formsTrees | `false` |
| stanceEffect | 无 |
| 颜色 | blue |

**对来源消息（sourceMessageId）的布局影响：**

| 目标类型 | 列约束 | 说明 |
|----------|--------|------|
| 普通文本消息（whole） | 来源列 ≥ 目标列 + 1 | 注释者必须在被注释消息的**右侧**（Stage 1-①） |
| 文本片段（text-fragment） | 同上 | 基于片段所属消息的列号 |
| 关系消息 | 来源列 ≥ 该关系消息所有普通端点最右列 + 1 | 注释指向关系消息时，来源必须在关系涉及的所有文本消息的最右侧 |

**对目标消息的布局影响：**
- 目标消息位置不受影响（只作为列约束的参照）
- 文本片段目标会高亮渲染（黄色/蓝色背景 + 边框）
- 连线从来源卡片指向目标卡片（或目标文本片段的 DOM 矩形）

#### REFERENCE（引用）

| 属性 | 值 |
|------|-----|
| PresentationKind | `edge-label` |
| formsTrees | `false` |
| stanceEffect | 无 |
| 颜色 | indigo |

布局影响与 ANNOTATION **完全相同**（共用同一套列约束逻辑 `computeMinColumnsForAnnoRefRule1`），仅标签文字和颜色不同。

#### REPLY（回复）

| 属性 | 值 |
|------|-----|
| PresentationKind | `edge-label` |
| formsTrees | `true` ✅ |
| stanceEffect | 无 |
| 颜色 | blue |

**对来源消息的布局影响：**

| 目标类型 | 列约束 | 说明 |
|----------|--------|------|
| 普通文本消息 | 来源列 ≠ 目标列，由作者通道优化确定 | 回复者不可与被回复者同列；同作者多条回复尽量对齐同一列（author-lane optimization） |
| 关系消息 | 来源列 ≥ 该关系消息所有普通端点最右列 + 1 | 与 anno/ref 到关系消息的约束一致 |

**对目标消息的布局影响：**
- 目标消息位置不受直接影响
- **树结构**：`formsTrees=true`，回复消息在树视图中成为目标消息的**子节点**（`buildMessageTree` 中将 `sourceMessageId` 作为 child，`targetRef` 作为 parent）

**作者通道优化（Author-lane optimization）：**
`applyReplyLayoutAdjustmentsWithConstraints` 中，同一作者的多条回复优先分配到同一列或相邻列（通过 `authorAnchor` 众数和 `authorPrevLane` 链式分配），减少视觉跳跃。

> **与注释/引用的区别**：ANNOTATION/REFERENCE 通过 `computeMinColumnsForAnnoRefRule1` 强制 `来源列 ≥ 目标列 + 1`（必须在右侧）。REPLY 不同——它仅禁止来源与目标同列（`forbidden` 集），实际列位置由作者通道优化算法（`authorAnchor` + `authorPrevLane`）在可选列中择优确定，因此回复可以出现在被回复者的左侧或右侧。

### 第二类：装饰标注（AGREE / DISAGREE）

> **PresentationKind**: `decoration` — 渲染为目标卡片右侧的彩色徽章。

#### AGREE（赞同）

| 属性 | 值 |
|------|-----|
| PresentationKind | `decoration` |
| formsTrees | `false` |
| stanceEffect | `support` |
| 颜色 | green |

**对来源消息的布局影响：**

| 场景 | 列约束 | 说明 |
|------|--------|------|
| 有来源文本消息 → 目标为普通消息 | 来源列 = 目标列 | 赞同者与被赞同消息**同列**，视觉对齐表达"我同意这个" |
| 有来源文本消息 → 目标为关系消息 | 来源列 = 被装饰关系端点列 | 指向关系消息的装饰徽章位置 |
| 纯立场（sourceMessageId = null） | 无列约束 | 不产生来源卡片，仅在目标右侧渲染绿色"赞同"徽章 |

**对目标消息的布局影响：**
- 目标消息位置不受影响
- 右侧渲染绿色徽章：显示赞同计数，位于卡片右上角
- 徽章拆分：左侧图标区（可点击快速发送空赞同）+ 右侧主体区（可点击选中）

#### DISAGREE（反对）

| 属性 | 值 |
|------|-----|
| PresentationKind | `decoration` |
| formsTrees | `false` |
| stanceEffect | `oppose` |
| 颜色 | red |

**对来源消息的布局影响：**

| 场景 | 列约束 | 说明 |
|------|--------|------|
| 有来源文本消息 → 目标为普通消息 | 来源列 = 目标列 + 1 | 反对者在目标**右侧一列**，视觉对比表达"我反对这个" |
| 有来源文本消息 → 目标为关系消息 | 来源列 = 被装饰关系端点列 + 1 | 向右偏移一列 |
| 纯立场（sourceMessageId = null） | 无列约束 | 仅在目标右侧渲染红色"反对"徽章 |

**对目标消息的布局影响：**
- 与 AGREE 相同，渲染红色徽章（位于绿色赞同徽章下方，间距 `DEC_GAP=4px`）

> **注意**：AGREE/DISAGREE 的列约束在 `applyAgreeDisagreeColumnOverride` 中执行，晚于 anno/ref/reply 约束（Stage 1-③），但早于 grouping（Stage 1-④）。赞同/反对在回复建立的对话结构之上叠加"站队"空间——同列为"我方"、右偏一列为"对方"，形成辩论双方的空间分布。

---

### 第三类：标签标注（TAG）

> **PresentationKind**: `decoration-label` — 渲染为目标卡片右侧的文字标签徽章。

| 属性 | 值 |
|------|-----|
| PresentationKind | `decoration-label` |
| formsTrees | `false` |
| stanceEffect | 无 |
| 颜色 | yellow |

**对来源消息的布局影响：**
- TAG 的来源消息（`sourceMessageId`）如果是普通文本消息且**仅**用于 TAG 关系，则从视图中**完全隐藏**（`tagSourceIds` 过滤）
- 标签文字取自 `relationLabel`（payload.label），聚合显示在目标右侧

**对目标消息的布局影响：**
- 目标消息位置不受影响
- 右侧渲染黄色文字标签徽章，位于赞同/反对徽章下方
- 相同文字内容的多个 TAG 会**聚合**为一个标签（多个 `relMsgIds` 合并），减少视觉杂乱
- 标签宽度自适应文字长度（`TAG_MIN_W=36px` 起，最多显示 20 字符）

| 目标类型 | 布局影响 |
|----------|----------|
| 普通文本消息 | 徽章在卡片右侧，赞同/反对徽章下方 |
| 关系消息（如 arrange、tag 等） | 徽章渲染在该关系消息的视觉元素旁（如排列边框旁、连线标签旁等） |

### 第四类：更正（CORRECT）

> **PresentationKind**: `correction-badge` — 渲染为来源卡片头部的小徽章。

| 属性 | 值 |
|------|-----|
| PresentationKind | `correction-badge` |
| formsTrees | `true` ✅ |
| replacesTarget | `true` ✅ |
| stanceEffect | 无 |
| 颜色 | yellow |

**对来源消息的布局影响：**

| 场景 | 列约束 | 说明 |
|------|--------|------|
| 有来源文本消息（非 anon） | 来源列 = 目标列 | 来源与目标**同列紧贴堆叠**（`applyGroupingColumnOverride` 中 `groupSourceToTarget` 映射） |
| 来源为 anon:（无替换内容） | 无来源卡片 | 仅标记目标为"空白更正" |

**对目标消息的布局影响：**

| 场景 | 效果 |
|------|------|
| 有替换来源（非 anon source）→ 目标为普通消息 | 目标卡片**隐藏**（`hiddenCorrectedTargetIds`），替换来源卡片显示在同列同位置，头部带"✏更正"徽章 |
| 有替换来源 → 目标为关系消息 | 目标关系消息的对应边**隐藏**（`correctedEdgeIdsByRelMsg`），替换关系的边在同位置显示 |
| 无替换来源（anon source）→ 目标为普通消息 | 目标卡片**保持可见**，仅头部显示更正徽章（`isBlankCorrected`） |
| 无替换来源 → 目标为关系消息 | 目标关系消息的边隐藏，仅显示更正徽章（`anonCorrectedRelMsgIds`） |

> **链式更正**：如果消息 A 更正消息 B，同时消息 B 也更正消息 C，则 B 保持可见（不被隐藏），以确保 B 自身的更正徽章不丢失。

### 第五类：边框包裹（ARRANGE / MERGE）

> **PresentationKind**: `arrange-frame` / `frame-group` — 渲染为包裹目标消息的可见边框。
>
> 两者同属边框类关系，将一组目标消息包裹在可视边框中。**核心区别在于目标消息的排布方式**：ARRANGE 按关系指定的方向**重新排列**目标消息；MERGE **保持**目标消息在列分配管线中确定的原始相对位置。

#### ARRANGE（排列）

| 属性 | 值 |
|------|-----|
| PresentationKind | `arrange-frame` |
| formsTrees | `true` ✅ |
| groupsTargets | `true` ✅ |
| stanceEffect | 无 |
| 颜色 | purple |
| sourceMessageId | 始终为 null（与会者到消息的关系） |

**对来源消息的布局影响：**
- `sourceMessageId` 始终为 null（与会者操作），无来源卡片

**对目标消息的布局影响：**

| 目标类型 | 列约束 | 排布方式 |
|----------|--------|----------|
| 多个普通文本消息 | 所有目标**强制同列** | `targetLayout='single-column'`（默认）：按创建时间**垂直堆叠重排**，紧贴无间距 |
| 多个普通文本消息 | 所有目标**强制同行** | `targetLayout='single-row'`：**水平排列重排**，x 递增 CARD_W + COL_GAP |
| 关系消息（嵌套排列） | 子排列边框嵌入父排列边框内 | 递归计算子边框的包围矩形，嵌入父边框 |

#### MERGE（归并）

| 属性 | 值 |
|------|-----|
| PresentationKind | `frame-group` |
| formsTrees | `false` |
| groupsTargets | `true` ✅ |
| stanceEffect | 无 |
| 颜色 | gray |
| sourceMessageId | 始终为 null |

**对来源消息的布局影响：**
- 无来源卡片

**对目标消息的布局影响：**

| 目标类型 | 列约束 | 排布方式 |
|----------|--------|----------|
| 多个普通文本消息 | 不强制同列 | 保持各消息间的**相对行列偏序**（谁在谁左边、谁在谁上边不变），但边框内不再有其他消息，因此行列上自然相邻、紧凑靠拢；整体用灰色边框包裹 |
| 关系消息（嵌套排列/分类/归并） | 子边框嵌入父归并边框 | 递归计算子关系包围矩形，纳入归并边框 |

#### 两者的关键区别

| 对比维度 | ARRANGE | MERGE |
|----------|---------|-------|
| 目标排布 | **重新排列**：全部强制同列（或同行），忽略原有列分配 | **保持偏序**：相对行列大小关系不变（左/右、上/下），但边框内仅有被归并的消息，行列间自然紧凑相邻 |
| 列约束 | `applyGroupingColumnOverride` 强制所有目标同列 | 不强制同列，各消息按已有列位置排布 |
| 布局方向 | 由 `payload.targetLayout` 控制（`single-column`/`single-row`） | 无方向概念，相对方位由列分配管线已确定 |
| 边框标题 | 无额外标题头 | 边框上方有卡片式标题头（`MERGE_CARD_H=36px`） |
| 标题内容 | — | `payload.title` → `payload.label` → 默认"归并" |

#### 边框渲染（共用逻辑）

- 边框包围盒外边距 `FRAME_PAD=16px`（边框矩形相较于内容包围盒的向外扩展量）
- 边框可点击（选中整个关系）
- 若被空白更正（anon CORRECT），边框隐藏但更正徽章保留
- 嵌套边框通过 `buildFrameBlocks` 的 subset 检测建立父子关系
- 递归布局：子边框作为父边框的一个"项目"，参与父边框内的排布

#### 归并边框特殊处理

- `applyMergeCanvasReservations`（Stage 2-⑪）：将归并区域内卡片向上压缩，区域外重叠卡片向下推开
- `applyFrameAvoidanceReservations`（Stage 2-⑩）：安全网，确保归并边框下方卡片不被覆盖
- 归并边框内的子边框会向右/向下扩展归并边框的包围矩形

> **归并对整体布局的连锁影响**：消息被归并到框架中后，除了框架内部需要紧凑排布，其原本所在位置也会空出。这产生两个连锁效应——一方面，同列中位于归并消息上方的非归并消息失去了下方的"支撑"，可能需要向上收紧间距；另一方面，归并框架作为一个整体的新位置可能与画布上其他消息重叠，需要将下方消息推开。这两点在设计归并布局时需要一并考虑，否则会出现多余空隙或重叠。

### 第六类：主题卡片（CLASSIFY / SUMMARY）

> **PresentationKind**: `edge-label` — 渲染为画布上的主题卡片（非 SVG 边框）。

#### CLASSIFY（分类）

| 属性 | 值 |
|------|-----|
| PresentationKind | `edge-label` |
| formsTrees | `false` |
| groupsTargets | `false` |
| stanceEffect | 无 |
| 颜色 | gray |

**对来源消息的布局影响：**
- 无来源卡片（`sourceMessageId` 为 null，与会者操作）

**对目标消息的布局影响：**
- CLASSIFY 关系消息本身作为**主题卡片**渲染在画布上（`topicRelMsgIds`），显示"分类 分类名" + 目标数量
- 被分类的原始消息在非线性结构视图和线性结构视图中均**不显示**——它们被移到另一个独立的分类子画布中，当前画布只保留分类消息卡
- 主题卡片参与普通卡片的列分配和无重叠排布

#### SUMMARY（总结）

| 属性 | 值 |
|------|-----|
| PresentationKind | `edge-label` |
| formsTrees | `false` |
| groupsTargets | `false` |
| stanceEffect | 无 |
| 颜色 | amber |

布局影响与 CLASSIFY 类似，但有关键差异：SUMMARY 关系消息作为**主题卡片**渲染，覆盖被总结的消息——被选中的消息在非线性结构视图中**不显示**（被总结卡覆盖），但在**线性结构视图中仍然可见**（保留原始发言记录）。

## 三、列分配优先级总结

各关系类型在列冲突中按覆盖优先级排序——**数字越小越优先，管线中后执行的步骤覆盖先执行的步骤**：

> **管线执行顺序为 ①→②→③→④，但覆盖优先级是 P1 > P2 > P3 > P4。**
> 这是因为 ①（anno/ref）必须最先执行，为所有后续步骤建立不可违背的列下限（"地板值"）；
> ②（reply）在地板值上做作者通道优化；③（agree/disagree）覆盖回复的列选择；
> ④（grouping）最后执行，强制同列约束覆盖前面所有结果。

```
覆盖优先级 P1 (最高，管线最后执行)：分组约束
    CORRECT → 来源与目标同列（原位替换）
    ARRANGE → 所有目标强制同列或同行
    MERGE   → 目标间保持偏序、紧凑靠拢

覆盖优先级 P2 (中高，管线最先执行)：注释/引用约束
    ANNOTATION、REFERENCE → 来源在目标右侧 (+1列)

覆盖优先级 P3 (中低)：赞同/反对约束
    AGREE  → 来源与目标同列
    DISAGREE → 来源在目标右侧一列

覆盖优先级 P4 (最低)：回复约束
    REPLY → 来源在目标一侧（交替） + 作者通道优化
```

> CLASSIFY 和 SUMMARY 不参与上述列约束（为 `edge-label` kind），它们的列位置由 anno/ref/reply 基础约束独立决定。

### 各列约束的会议语义

| 约束 | 列效果 | 会议场景含义 |
|------|--------|------------|
| 注释/引用在目标右侧 | 来源列 ≥ 目标列 + 1 | "我对这段话有补充/引证"——注释者站在被注释内容的旁边，不打断原文的阅读流 |
| 回复在目标一侧 | 来源列 ≠ 目标列 | "我回应你的发言"——回复交替出现在被回复者的左侧或右侧，形成类似私聊界面的对话链 |
| 赞同与目标同列 | 来源列 = 目标列 | "我站在你这边"——视觉上紧密对齐，赞同者与被赞同者融为一体 |
| 反对在目标右侧一列 | 来源列 = 目标列 + 1 | "我不同意，但仍在讨论同一分类"——保持适当距离，形成对峙但不远离 |
| 排列同列/同行 | 所有目标同列或同行 | 同列：这几条发言属于**同一个论点**；同行：这几条发言是**同一个问题的不同论点** |
| 归并保持偏序 | 保持相对方位、紧凑靠拢 | 将现有讨论结构固定下来，方便他人浏览；当前为自动紧凑布局，未来可能支持手动调整或其它框架内排布方式 |
| 更正同列替换 | 来源列 = 目标列 | "修正已有的说法"——更正直接覆盖被更正内容，原位替换 |
| 分类/总结 | 无列约束 | 分类：将选中消息移到独立子画布，当前视图只留分类卡；总结：用总结卡覆盖被选中消息，非线性视图隐藏、线性视图保留原始消息 |
| TAG 标注 | 无列约束 | "给这条消息打个标签"——方便后续按标签检索和归类，不改变消息位置 |
