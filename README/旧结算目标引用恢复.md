# 旧结算消息的目标引用恢复

数据库版本 8：`restore-historical-settlement-targets`。恢复逻辑属于独立的 `apps/migrate` 迁移程序。API 启动发现待升级版本时，会调用同一迁移程序；也可以在发布窗口中先手动预检、执行，再启动 API。

旧导入程序只为有 `relationType` 的消息创建目标关系，遗漏了 `relationType = null` 的 `ROUND` 和 `ROUND_RESULT`。后续格式转换又清除了兼容字段。此次修复同时覆盖新导入、旧格式转换、已升级数据库的补救，以及旧阅览文件转换。

迁移优先读取当前库的 `legacy_records`，缺少时尝试迁移前的 `message_format_backups`。使用原记录里的准确 ID，不按正文或时间推断目标。恢复消息、历史版本、执行记录和引用索引，追加同步事件使浏览器缓存收到修复。已有显式目标保持不变。消息 ID、修订号、原文及时间保持不变，不执行结算、支付或重放旧交易。迁移事务会校验余额和账本指纹；失败整体回滚，版本 8 不会登记。重复执行不会追加恢复事件。

## 生产库仍保留原始归档

先发布包含此修复的候选镜像。以下命令在**新云服务器的部署仓库根目录**执行，沿用现有 Compose 项目、配置和当前业务 schema。`GONGLUN_IMAGE` 须指向包含版本 8 的镜像。若应用运行时已自动切换到其他 schema，手动命令也须使用该实际业务 schema；现有维护脚本会显示正在运行的库和 schema。

1. 用现有维护入口备份当前生产库：`bash deploy/manage.sh backup`。
2. 安排维护窗口，停止 API 写入，保留 PostgreSQL 服务运行。
3. 用候选镜像预检、执行和验证：

```bash
compose=(docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env.prod)
"${compose[@]}" stop api
"${compose[@]}" run --rm --no-deps -T api node apps/migrate/dist/migrate-cli.js --plan
"${compose[@]}" run --rm --no-deps -T api node apps/migrate/dist/migrate-cli.js
"${compose[@]}" run --rm --no-deps -T api node apps/migrate/dist/verify-current-cli.js
"${compose[@]}" up -d api
```

预检中的 `settlementTargets.pending` 是待补引用的消息数量，`unresolved` 应为 0；这里的数量以生产实际数据为准。验证应返回 `verified: true`，并且 `settlementTargets.pending`、`settlementTargets.unresolved` 都为 0。验证会核对消息/账户/归属的执行记录重放、引用索引和历史结算引用。最后按 ID 打开此前缺引用的结果消息，并检查目标标签。

也可以通过正常发布流程启动新版 API，让它自动执行版本 8。仍应先备份，完成后运行上述只读验证。只更新代码文件而没有发布对应镜像，不会更新生产迁移程序。

## 当前库缺少归档时，使用新云服务器的 deploy/backups

如果预检显示 `unresolved > 0`，迁移会停止。可以使用 `deploy/backups` 中从以前服务器带来的完整旧数据库备份：

1. 执行 `bash deploy/manage.sh restore`，从备份列表中选择原始备份，恢复到一个**新的临时数据库**，如 `gonglun_settlement_source_20261023`。脚本不会自动切换网站数据库。不要把临时库名写入当前生产的 `GONGLUN_DATABASE_NAME`。
2. 核对备份时间、校验文件及业务 schema。临时库应包含旧 Prisma 的 `Message` 表，或新版库保留的 `legacy_records` 原始归档；仅包含展示文本的导出不能替代准确引用。
3. 在当前终端设置迁移专用的备份源连接。URL 指向刚恢复的临时库；不要改变目标库的 `DATABASE_URL`。可以采用临时库的只读账号，连接密码不写入命令历史：

```bash
read -r -s -p '临时备份库连接 URL：' GONGLUN_SETTLEMENT_SOURCE_DATABASE_URL
echo
export GONGLUN_SETTLEMENT_SOURCE_DATABASE_URL
export GONGLUN_SETTLEMENT_SOURCE_DATABASE_SCHEMA=public
```

容器内连接同一 PostgreSQL 服务时，主机名为 `postgres`；数据库名使用临时库名，业务 schema 以备份实际情况为准。

4. 在同一维护窗口中，把这两个变量仅传给独立迁移程序，先预检再执行：

```bash
compose=(docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env.prod)
"${compose[@]}" stop api
"${compose[@]}" run --rm --no-deps -T \
  -e GONGLUN_SETTLEMENT_SOURCE_DATABASE_URL \
  -e GONGLUN_SETTLEMENT_SOURCE_DATABASE_SCHEMA \
  api node apps/migrate/dist/migrate-cli.js --plan
"${compose[@]}" run --rm --no-deps -T \
  -e GONGLUN_SETTLEMENT_SOURCE_DATABASE_URL \
  -e GONGLUN_SETTLEMENT_SOURCE_DATABASE_SCHEMA \
  api node apps/migrate/dist/migrate-cli.js
"${compose[@]}" run --rm --no-deps -T api node apps/migrate/dist/verify-current-cli.js
"${compose[@]}" up -d api
unset GONGLUN_SETTLEMENT_SOURCE_DATABASE_URL GONGLUN_SETTLEMENT_SOURCE_DATABASE_SCHEMA
```

备份源连接以只读事务读取；只修复目标生产库的缺失引用。源库和已有生产数据不会被旧快照替换。备份不包含目标、目标消息已不存在或引用无法解析时，迁移报错并回滚，不会猜测补值。验证通过后，临时库可按既有维护流程另行清理。

## 回退

执行失败时事务回滚，原版本保持不变。成功升到版本 8 后，旧镜像会拒绝这个更新后的数据库版本；不能只回退镜像。需要按现有维护流程，把升级前备份恢复到新数据库后切换，并保留升级后的库及维护窗口之后的新数据。
