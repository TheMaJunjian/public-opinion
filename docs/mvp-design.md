# 公论（public-opinion）MVP 设计文档

## 1. 文档目的

- 基于当前 Demo 行为（含已讨论交互）定义 MVP 产品设计，并向"消息 + 关系消息"非线性结构系统演进。
- 明确可交付范围、核心概念、关键流程与验收标准。
- 本文档聚焦产品与交互，不包含实现代码或技术细节。

## 2. 产品目标与核心理念

### 2.1 核心目标

- 让用户像日常聊天一样"发消息/读消息"，但获得数据库式的结构化能力：记录、引用、注释、表态、修订、归并、总结等。
- 支持围绕同一议题进行结构化讨论，降低线性聊天中的信息混乱。
- 让"消息"与"消息间关系"可追踪、可视化、可回溯、可递归。
- 所有可视化与交互设计都服务于一个核心：**让用户更清楚理解消息之间的关系，降低认知负担**。
- 当前的显示方式仅为暂定方案，后续可替换为更优的方案；架构必须支持演进，而不是被某种展示形态锁死。

### 2.2 关键哲学

- **消息是最重要的实体**。所有操作本质上是增加数据库记录。
- "关系"不是隐藏在系统里的属性，而是一等公民：用"关系消息"承载关系本身，使其可见、可操作、可追溯、可再被关系化。
- 同时提供：
  - 线性列表视角（便于阅读与编辑关系过程）
  - 非线性图视角（便于理解结构与关联）

## 3. MVP 范围

### 3.1 In Scope（本期范围）

- 基础关系类型：**注释（annotation）**、**引用（reference）**、**回复（reply）**、**赞同（agree）**、**反对（disagree）**、**支持（support）**、**反驳（rebut）**。
- 消息级与片段级关系建立（整条消息或选中文本片段）。
- **关系消息也可作为目标**：关系消息的点击区（如边标签、装饰）可作为 Targets 中的目标。
- 关系建立流程：
  - 从草稿选择 sources（仅文本消息及其片段） / targets（可包含文本消息/片段及关系消息/片段）
  - 与已有消息建关系
  - 新建消息并立即建立关系
- 双视图：
  - 线性列表视图
  - 非线性图视图（关系消息作为可交互实体，不仅是图边）
- 非线性图视图中关系消息的可视形态：带标签点击区的连接元素（注释/引用/回复）、装饰（赞同/反对）、连接元素 + 装饰的组合（支持/反驳）。
- 焦点模式（Focus Mode）：基于 hop 距离裁剪子图显示。
- 导入脚本/数据的概念性格式（用于初始化消息与关系）。

### 3.2 Out of Scope（本期不做）

- 更正（correction）、分类（classify）、归并（merge/group）、总结（summary）、推荐（recommend）、冷藏（freeze/archive）等高级关系类型。
- 自动布局最优解（全局最优、复杂避让算法）。
- 协同编辑冲突处理、权限系统细粒度策略、审计策略完善。
- 智能摘要、推荐、自动关系推断。

## 4. 用户角色（MVP）

- **普通参与者**
  - 浏览消息
  - 选择整条或片段
  - 发起各类关系
- **组织者/主持者（同权限模型下的高频用户）**
  - 组织讨论结构
  - 校验关系是否准确
  - 使用双视图进行引导与复盘

> MVP 阶段角色主要体现为使用方式差异，不强调复杂 RBAC。

## 5. 核心概念

### 5.1 消息分两类

**文本消息（Normal/Text Message）**

- 承载内容（文本字段）、作者、时间等。
- 在非线性结构视图中以"消息卡片"形式展示（后续可演进）。
- 整个卡片是点击区（用于选中切换、作为操作入口）。

**关系消息（Relation Message）**

- 关系消息也是消息，拥有自己的 id、作者、时间、内容/元数据、点击区与选中状态。
- 关系消息的作用是：直观显示消息之间的关系，并提供交互入口。
- 关系消息可以指向：
  - 文本消息整体
  - 文本消息的文本片段（字段/片段）
  - 关系消息整体
  - 关系消息的"片段/点击区"（如边的标签、装饰、框架边界等）
- **必须支持"对关系消息再次建立关系"**（递归）。

### 5.2 关系类型（当前支持，不设"主流"）

当前支持的关系类型（不同类型有不同显示方式与布局影响策略）：

| 类型 | 说明 |
|------|------|
| annotation | 注释 |
| reference | 引用 |
| reply | 回复 |
| agree | 赞同 |
| disagree | 反对 |
| support | 支持（表态 + 结构指向） |
| rebut | 反驳（表态 + 结构指向） |

> 后续可扩展：correction（更正）、classify（分类）、merge/group（归并）、summary（总结）、recommend（推荐）、freeze/archive（冷藏）等。

### 5.3 关系消息的点击区（SelectablePart）

每种关系消息都提供稳定的"点击区/片段"（SelectablePart），用于：

- Draft 目标选择
- 焦点模式裁剪与重建
- 在关系消息上再建关系（递归）

### 5.4 关系消息 ≠ 图边（重点更正）

- **关系消息不等于有向边**。有向边只是某些关系消息在某些视图下的暂定呈现方式之一。
- 每种关系消息类型有最适合其语义的显示与布局方式：
  - 注释/引用/回复 → 带标签点击区的可交互连接元素（类似有向边 + 标签）
  - 赞同/反对 → 文本消息上的装饰（显示计数，点击查看明细）
  - 支持/反驳 → 装饰 + 连接元素组合

## 6. 概念数据模型（非实现）

- **Topic（议题）**
  - 承载一组消息与关系
- **User（用户）**
  - 关系与消息的作者
- **Message（消息，统一实体）**
  - kind: "text" | "relation"
  - 内容、作者、时间等基础信息
- **Relation（关系消息的结构化元数据）**
  - type: 关系类型（annotation/reference/reply/agree/disagree/support/rebut/…）
  - sources: 来源端（文本消息或其片段，不含关系消息）
  - targets: 目标端（文本消息/片段，或关系消息/片段）
  - 可选 fragment（片段范围/文本定位信息）
  - author（关系发起者）
- **SelectableTarget（可被指向/选中的点击区/片段抽象）**
  - 文本片段（start/len 或字段 path）
  - 消息整体
  - 关系消息的某个可交互部件（如 label、decoration、frame）
- **PresentationSpec（关系消息的显示规格）**
  - 每个 spec 定义：点击区、选中片段集合、布局影响策略
  - 例如：EdgeLabel（连接元素）、Decoration（装饰）、ReplaceOverlay（更正/总结）、FrameGroup（分组框架）

## 7. 选中、候选区与来源/目标集合（严格约束）

### 7.1 Draft（候选区）规则

**来源集合（Sources）规则：**
- 只能包含文本消息及其片段。
- 不能包含关系消息或关系消息片段。

**目标集合（Targets）规则：**
- 可包含文本消息/片段，也可包含关系消息/片段。

### 7.2 关系消息的选中行为

- 单击关系消息的点击区：选中该关系消息的对应"片段"（如边标签片段、装饰片段）。
- 双击关系消息的点击区：选中该关系消息的"全部片段"（相当于全选该关系消息）。

## 8. 关键用户流程

### 8.1 选择目标：整条消息 / 片段 / 关系消息点击区

- 用户可直接选择文本消息卡片（整条）。
- 用户也可在消息内容中选中文本片段作为关系目标。
- 用户可单击关系消息的点击区，将其选入目标集合（用于对关系消息再建关系）。

### 8.2 草稿阶段：draft -> sources / targets

- 用户在草稿态先明确：
  - source（关系发起消息，仅文本消息）
  - target（关系目标，可多目标，含关系消息点击区）
- 草稿中可切换关系类型。

### 8.3 建关系：已有消息 或 新消息

- **路径 A：已有消息**
  - 选择已有 source 和 target 后直接生成关系。
- **路径 B：新建消息**
  - 先输入新消息内容
  - 以该新消息作为 source（或按交互约定作为 target）建立关系
  - 一次完成创建与关联

## 9. 视图设计

### 9.1 线性列表视图

- 按时间/上下文阅读消息流。
- 显示文本消息与关系消息。
- 关系消息用于表达"谁对谁做了什么关系、指向整条或片段"。

### 9.2 非线性图视图

- 显示文本消息卡片与关系消息的可视实体（连接元素、装饰、框架等）。
- 关系消息按类型以最合适的形态呈现（不默认全部渲染为有向边）：
  - **注释/引用/回复**：带标签点击区的可交互连接元素（有向边 + 标签），标签格式：`author · 注释/引用/回复`
  - **赞同/反对**：在文本消息上添加装饰（显示计数），装饰为点击区
  - **支持/反驳**：装饰（计数） + 连接元素（指向装饰点击区），连接元素标签为点击区
- 每种渲染实体都提供稳定的点击区/片段 id，用于选中、Draft 选择与焦点裁剪。

### 9.3 焦点模式（Focus Mode）

- 目的：只显示与焦点相关的"局部子图"，降低认知负担，不全量显示。
- **hop 的正确定义**：
  - hop 表示：文本消息与另一条文本消息之间，经过多少个关系消息连接（以关系消息为中间节点的步数/段数）。
  - hop = 1：与焦点文本消息直接相连的文本消息。
- **裁剪规则**：
  - 仅显示符合 hop 距离的文本消息。
  - 关系消息仅在两端文本消息**都显示**时才显示（含递归关系）。
  - 焦点裁剪的主轴是"文本消息"，关系消息的显示依赖于文本消息是否同时在子图中可见。

## 10. 布局与可视化规则

### 10.1 文本消息卡片布局

- 列布局目标：尽量满足 `col(from) = col(to) + 1` 的阅读意图（从右向左回看目标）。
- 卡片规则：
  - 等宽
  - 高度随内容变化
  - 卡片四周需预留足够空白间距，确保关系消息有足够空间展示
- 位置规则：
  - 无关系消息优先靠左上排列
  - 有关系的消息优先放在其目标右侧；右侧不可用时向下排布
  - 减少无效空白，保证信息密度与可浏览性

### 10.2 关系消息布局影响策略

- 注释/引用/回复类连接元素：可能影响相关文本消息的列/层级排布。
- 赞同/反对装饰：可能影响卡片周边占位。
- 分组框架（后续）：可能引入群组布局约束。

### 10.3 显示稳定性要求

- 不调整布局时，消息的绘制应保持稳定：
  - 除状态变化（选中/高亮/展开/折叠）外，不应因无关消息改变绘制形态。
  - 调整无关消息布局时，不应影响其他消息的绘制。
- 连线规则：
  - 锚点落在卡片边缘或片段边缘（或装饰点击区）
  - 使用曲线边，减少遮挡
  - 方向明确、标签就近可读

## 11. 脚本/导入格式（概念）

- 支持通过结构化脚本一次导入：
  - 用户（可选）
  - 文本消息
  - 关系消息（含类型、sources/targets、可选片段）
- 导入后应能直接在列表与图视图得到一致投影结果。
- 片段关系导入需包含稳定定位信息（概念上可由文本范围或锚点描述）。

## 12. 已知问题与待修复方向

- 某些场景下，图边起终点与卡片边缘/片段高亮存在可见偏移。
- 对"片段引用"的图视图呈现存在不稳定现象（整条消息引用通常正常）。
- 非线性视图在特定关系密度下仍可能出现对齐与空白利用不理想的情况。
- **"关系消息也是消息"未真正实现**：
  - 给关系消息建立关系时，目标集合指向有问题（应指向关系消息自身的点击区，而不是该关系连接到的文本消息）。
- **焦点模式 hop 语义需修正**：应按"文本消息之间经过关系消息数"实现，不是按普通图距离。

## 13. 验收标准（Acceptance Criteria）

- 支持的关系类型：annotation、reference、reply、agree、disagree、support、rebut。
- 关系消息在非线性图视图中按类型以正确形态呈现（连接元素 / 装饰 / 组合）。
- 关系消息的点击区稳定可选中（单击选片段，双击全选）。
- Sources 集合只能包含文本消息及其片段，不能包含关系消息。
- Targets 集合可包含文本消息/片段及关系消息/片段（点击区）。
- 对关系消息的点击区建立关系时，目标指向该关系消息点击区，而非其连接的文本消息。
- 焦点模式裁剪按 hop 距离（以关系消息为中间节点）正确显示子图。
- 关系消息仅在两端文本消息都在焦点子图中可见时才显示。
- 用户可完成以下流程：
  - 选择整条文本消息并建关系
  - 选择消息片段并建关系
  - 草稿中设置 sources/targets（含关系消息点击区为 target）
  - 与已有消息建关系
  - 新建消息并建立关系
- 图布局满足 MVP 规则：等宽卡片、可变高、曲线边、锚点贴边、尽量减少无效空白。
- 非线性视图显示稳定：无关消息布局调整不改变其他消息的绘制形态。

## 14. Roadmap（后续规划）

- **M1（当前）**：纠正"关系消息作为目标"的指向与选中
  - 关系消息的点击区（如边标签）作为稳定 SelectablePart
  - 边指向关系消息点击区，而非关联的文本消息
  - Sources / Targets 集合约束正确执行
- **M2**：焦点模式裁剪重做
  - hop 语义按"文本消息之间经过关系消息数"实现
  - 仅显示符合 hop 的文本消息；关系消息仅在两端可见时才显示
- **M3**：关系显示抽象层（PresentationSpec）
  - 将"某些关系渲染为边、某些关系渲染为装饰"的逻辑从 GraphView 中抽象出来
  - 为后续更正/分组/总结/推荐等关系类型留出明确扩展点
- **M4**：更多关系类型
  - correction（更正）：差异字段标注，替换/覆盖展示
  - classify/merge/group（分类/归并）：框架包围，群组布局
  - summary（总结）：总结消息遮盖框架集体
  - recommend/freeze（推荐/冷藏）：装饰 + 布局权重变化
- **M5**：协作能力扩展（权限、审阅流、版本追踪）与智能辅助。
