# 公论（public-opinion）MVP 设计文档

## 1. 文档目的

- 基于当前 Demo 行为（含已讨论交互）定义 MVP 产品设计。
- 明确可交付范围、核心概念、关键流程与验收标准。
- 本文档聚焦产品与交互，不包含实现代码或技术细节。

## 2. 产品目标

- 支持围绕同一议题进行结构化讨论，降低线性聊天中的信息混乱。
- 让“消息”与“消息间关系”可追踪、可视化、可回溯。
- 同时提供：
  - 线性列表视角（便于阅读与编辑关系过程）
  - 非线性图视角（便于理解结构与关联）

## 3. MVP 范围

### 3.1 In Scope（本期范围）

- 两类关系：**注释（annotation）**、**引用（reference）**。
- 消息级与片段级关系建立（整条消息或选中文本片段）。
- 关系建立流程：
  - 从草稿选择 sources / targets
  - 与已有消息建关系
  - 新建消息并立即建立关系
- 双视图：
  - 线性列表视图
  - 非线性图视图
- 图中边标签展示：**`author · 注释/引用`**。
- 导入脚本/数据的概念性格式（用于初始化消息与关系）。

### 3.2 Out of Scope（本期不做）

- 关系类型扩展（超过 annotation/reference 的类型）。
- 自动布局最优解（全局最优、复杂避让算法）。
- 协同编辑冲突处理、权限系统细粒度策略、审计策略完善。
- 智能摘要、推荐、自动关系推断。

## 4. 用户角色（MVP）

- **普通参与者**
  - 浏览消息
  - 选择整条或片段
  - 发起注释/引用关系
- **组织者/主持者（同权限模型下的高频用户）**
  - 组织讨论结构
  - 校验关系是否准确
  - 使用双视图进行引导与复盘

> MVP 阶段角色主要体现为使用方式差异，不强调复杂 RBAC。

## 5. 核心概念

### 5.1 消息（Message）

- 讨论中的基本内容单元。
- 可被其他消息整体关联，也可被片段关联。

### 5.2 关系（Relation）

- 仅两种：
  - 注释（annotation）
  - 引用（reference）
- 关系有方向（from -> to）。
- `to` 可指向：
  - 整条消息
  - 消息中的文本片段

### 5.3 关系消息 vs 图边（重点）

- **关系消息（Relation Message）**
  - 出现在**线性列表视图**
  - 用于阅读关系语义与上下文
- **图边（Edge）**
  - 出现在**非线性图视图**
  - 图中仅展示普通消息节点 + 关系边
  - 不单独渲染关系消息卡片

## 6. 概念数据模型（非实现）

- **Topic（议题）**
  - 承载一组消息与关系
- **User（用户）**
  - 关系与消息的作者
- **Message（消息）**
  - 内容、作者、时间等基础信息
- **Relation（关系记录）**
  - type: annotation/reference
  - fromMessageId
  - toMessageId
  - 可选 toFragment（片段范围/文本定位信息）
  - author（关系发起者）

> 视图投影原则：  
> 列表视图可见消息与关系消息；图视图仅以普通消息为节点、关系为边进行投影。

## 7. 关键用户流程

### 7.1 选择目标：整条消息 / 片段

- 用户可直接选择消息卡片（整条）。
- 用户也可在消息内容中选中文本片段作为关系目标。

### 7.2 草稿阶段：draft -> sources / targets

- 用户在草稿态先明确：
  - source（关系发起消息）
  - target（关系目标，可多目标）
- 草稿中可切换关系类型（注释/引用）。

### 7.3 建关系：已有消息 或 新消息

- **路径 A：已有消息**
  - 选择已有 source 和 target 后直接生成关系。
- **路径 B：新建消息**
  - 先输入新消息内容
  - 以该新消息作为 source（或按交互约定作为 target）建立关系
  - 一次完成创建与关联

## 8. 视图设计

### 8.1 线性列表视图

- 按时间/上下文阅读消息流。
- 显示普通消息与关系消息。
- 关系消息用于表达“谁对谁做了注释/引用、指向整条或片段”。

### 8.2 非线性图视图

- 仅显示普通消息节点与关系边。
- 关系消息不作为独立节点展示。
- 边标签统一展示：**`author · 注释/引用`**。

## 9. 布局与可视化规则（MVP 约束）

- 列布局目标：尽量满足 **`col(from) = col(to) + 1`** 的阅读意图（从右向左回看目标）。
- 卡片规则：
  - 等宽
  - 高度随内容变化
- 位置规则：
  - 无关系消息优先靠左上排列
  - 有关系的消息优先放在其目标右侧；右侧不可用时向下排布
  - 减少无效空白，保证信息密度与可浏览性
- 连线规则：
  - 锚点落在卡片边缘或片段边缘
  - 使用曲线边，减少遮挡
  - 方向明确、标签就近可读

## 10. 脚本/导入格式（概念）

- 支持通过结构化脚本一次导入：
  - 用户（可选）
  - 消息
  - 关系（含 annotation/reference、from/to、可选片段）
- 导入后应能直接在列表与图视图得到一致投影结果。
- 片段关系导入需包含稳定定位信息（概念上可由文本范围或锚点描述）。

## 11. 已知问题（Known Issues）

- 某些场景下，图边起终点与卡片边缘/片段高亮存在可见偏移。
- 对“片段引用”的图视图呈现存在不稳定现象（整条消息引用通常正常）。
- 非线性视图在特定关系密度下仍可能出现对齐与空白利用不理想的情况。

## 12. 验收标准（Acceptance Criteria）

- 仅存在且仅可创建两类关系：annotation、reference。
- 列表视图可展示关系消息；图视图不展示关系消息节点。
- 图视图仅有普通消息节点与关系边。
- 任一关系边标签格式为：`author · 注释` 或 `author · 引用`。
- 用户可完成以下流程：
  - 选择整条消息并建关系
  - 选择消息片段并建关系
  - 草稿中设置 sources/targets
  - 与已有消息建关系
  - 新建消息并建立关系
- 图布局满足 MVP 规则：等宽卡片、可变高、曲线边、锚点贴边、尽量减少无效空白。

## 13. Roadmap（后续规划）

- **M1（当前）**：双视图 + 两类关系 + 片段级关联 + 基础布局可读性。
- **M2**：布局稳定性优化（密集图避让、分层更稳）、片段锚点鲁棒性提升。
- **M3**：关系筛选/折叠、批量操作、导入校验与错误回显增强。
- **M4**：协作能力扩展（权限、审阅流、版本追踪）与智能辅助。
