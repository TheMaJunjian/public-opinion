# 推荐首页与首屏性能

## 入口与内容

普通登录和访问 `/` 显示讨论首页。`/?feed=following` 为关注，`/?feed=latest` 为最新；生产 HashRouter 对应 `/#/`。原 `/messages` 仍为完整消息工作台，`/?msg=...` 继续转到消息直达链接，登录前访问的消息地址继续保留。首次进入首页不会挂载工作台、创建全局消息目录或启动图计算。

首页每页默认 20 条，最大 30 条。只展示有正文的内容，排除系统账目、审核过程、纯结构操作、关系标签和单独的立场记录。摘要最多 420 字符，取当前消息记录的原文；不把未经确认的更正合成为结论。有更正记录时提示进入讨论查看版本。浏览摘要不写已阅状态。

推荐和关注把同一直接分类／正文依赖上下文下的内容合成一张讨论卡，最多附三条进展。第一版没有全图递归聚类，也不推断语义话题。最新按记录发布／更新序号倒序分页，不合并上下文。

## 第一版推荐规则

服务端从最近 180 条正文、最多 120 条关注候选，以及最近 80 条个人通知对应的正文中选候选。关注候选使用最近 200 条有效关注记录；支持直接关注消息、分类直接成员和正文的直接依赖上下文。深层分类订阅、全量关注历史和语义兴趣召回仍由后续迭代扩展，完整内容可从工作台或最新入口访问。

推荐分数由关注（60）、参与关联（30）、未阅（8）和递减的时效分（最高 14）组成。每五个位置尝试加入一条新发现，并在有其他作者候选时避免连续三条来自同一作者。参与关联使用本人消息及近期个人通知，不根据赞同倾向猜测用户立场。关注页按进展序号排列。

当前版本是可解释的规则推荐，没有训练机器学习模型，没有按押注或贡献点购买排名。分数仅控制发现顺序，不改变内容、关系生效或真假判断。

## 数据与分页

- `feed_entries` 保存可重建的正文摘要，按发布序号、作者、直接上下文建立索引。
- `feed_corrections` 保存更正记录到目标的查询索引。
- `feed_hidden` 仅保存本人减少展示的讨论编号，支持撤销，不进入公开账本和消息历史。
- 数据库版本 45 分批回填现有消息。内容提交时在原事务内更新索引，失败一并回滚。

推荐／关注的一批排序在服务进程中保留 10 分钟，只缓存消息编号与顺序，最多 128 批。后续页重新读取摘要、检查审核权限、个人屏蔽、冷藏、个人审核否决和隐藏偏好。游标绑定账户及栏目；过期、服务重启或落到另一个进程时返回 `FEED_EXPIRED`，前端保留已展示内容并提示刷新。多实例生产部署如需无感跨实例分页，应将这部分短期排序缓存迁到共享存储或启用会话路由。

最新采用发布序号与 ID 游标，固定本次浏览的序号上限；后来发布的内容在刷新后出现。审核隐藏过多时，单次最多扫描 400 条索引记录，仍可继续翻页。

所有响应为 `private, no-store`，不会进入离线缓存。审核权限在返回时重新验证，受限正文及依赖引用不会进入摘要。推荐请求失败时，前端尝试最新内容；仍失败则显示重试入口。切换栏目或账户取消旧请求，过期响应不能覆盖新页面。

## 性能观测与复测

浏览器 Performance Measures 提供 `entry:session`、`entry:login`、`entry:feed-request` 和 `entry:feed-ready`。其中 login 包含设备签名密钥准备；feed-ready 从首页请求开始到内容提交后的动画帧，不等同于完整页面 LCP。接口 `Server-Timing` 提供 feed 总耗时、数据库耗时和查询数量。

离线完整构建缓存在首页可阅读后等待 1.5 秒开始；没有首页信号时最迟 15 秒启动，用户主动打开本地阅览可立即启动。静态资源每批两个低优先级请求，完成全部资源后才标记离线就绪。

```sh
npm run build
npm run test:bundle
npx tsx scripts/feed-load.ts
```

规模测试只使用 `TEST_DATABASE_URL` 或本机开发 PostgreSQL，在独立随机测试 schema 内创建和清理合成数据，不使用部署 `DATABASE_URL`。报告默认写入 `data/performance/feed.json`。

本次本机验证（开启审核、合成普通消息、每档 25 次串行 HTTP 请求）：

| 正文数量 | 首次接口响应 | P95 接口响应 | 首屏响应体 |
| --- | --- | --- | --- |
| 100 | 40.07 ms | 35.80 ms | 9,856 B |
| 10,000 | 30.34 ms | 31.52 ms | 9,711 B |

构建检查确认首页的静态依赖不含工作台、目录引擎和 GraphView；推荐页自身约 2.9 KB gzip，连同公共 JS 静态依赖约 84 KB gzip。CSS、网络、认证和浏览器渲染耗时不包含在这些体积和接口数字中。

生产验收仍需在真实设备和网络下测量首次无缓存访问、已有会话、首次输入密码、消息直达四条路径，分别观察分段耗时及“登录成功到可阅读”的 P75。2 秒是目标，尚未作为生产实测结论。推荐首页改善默认入口；完整消息工作台仍需结构目录，具体讨论的范围加载见下文。

## 具体讨论的范围加载

`/messages?msg=...` 和 `/messages/:id` 默认走 `POST /api/ui/snapshot/discussion`，不启动全站目录、原窗口同步或目录 worker。原 `/messages` 保留完整浏览；显式 `catalog=full` 可用于完整目录对照验证。

首屏包含目标消息、最多 20 条直接关联内容／分类直接成员，以及完整的更正、立场、成员竞争与正文依赖上下文。未打开分类的子正文不进入响应。投影仅补齐当前页需要的引用，不为分类的全部成员逐条读取正文；原生消息 parts 保持不变。容器数量单独从成员索引统计。关联过于复杂、必要上下文超过 600 条或 40 轮展开时，接口明确返回 `DISCUSSION_TOO_LARGE`，提供完整工作台入口，不用截断的关系推断结果。

关联内容按序号倒序进行游标分页，每页替换画布，避免浏览越久画布越大。游标绑定地区、账户和查询范围，固定分页的发布序号上限；每次仍读取当前权限和正文，切换分类或跳转其他消息重新选择范围。追溯按请求的方向和距离展开，仍受上下文上限约束。筛选、对比和排行榜仅计算当前页及其必要上下文，界面明确说明该范围。范围模式不执行全量作者已阅回填，避免把局部关系当成完整阅读上下文。

客户端取消旧范围请求并丢弃迟到响应；失败时保留可读页面和重试入口，认证／目标可读权限失效则停止展示旧页面，权限恢复后重新发布。后台订阅变更，只重新请求当前范围；正文和投影未变化、仅序号或分页水位变化时不重建画布。选中已加载消息不发起范围请求、不重置页码；翻页保留选中消息作为必要操作上下文。分页与切换账户均重新验证服务端数据，不使用持久化的局部图作为全局目录。

复测命令（独立本地测试 schema）：

```sh
npx tsx scripts/feed-load.ts --discussion --output data/performance/discussion.json
npx tsx scripts/feed-load.ts --serve --discussion
```

2026-11-12 本机合成数据验证，开启审核、每档 25 次串行 HTTP 请求；与其他回归测试并行运行，数字仅用于本地量级观察：

| 正文数量 | 请求范围 | P95 接口响应 | 首屏响应体 |
| --- | --- | --- | --- |
| 100 | 具体消息 | 124.24 ms | 2,159 B |
| 100 | 大分类首屏 | 62.82 ms | 40,954 B |
| 10,000 | 具体消息 | 44.64 ms | 2,160 B |
| 10,000 | 大分类首屏 | 334.21 ms | 41,432 B |

这组测试覆盖无关消息增多和单个分类增宽，未代表复杂更正／立场链、并发高峰或生产设备的完整首屏耗时。浏览器另行验证直接登录到分类、翻页与返回，未出现原有的 30 秒绘制等待。范围接口沿用现有消息、引用和成员索引，本轮不增加数据库迁移版本。

本地视觉预览可使用 `npx tsx scripts/feed-load.ts --serve`，服务只监听本机 5187 端口，凭据为脚本内的合成测试账户。输入 `q` 并回车可关闭服务并清理测试 schema；强制杀死进程无法保证运行清理逻辑。
